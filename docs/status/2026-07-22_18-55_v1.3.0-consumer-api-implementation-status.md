## D) TOTALLY FUCKED UP

### D1: `FormatText` output format change is a behavioral breaking change

**Severity: HIGH**

`FormatText` output changed from `[ERROR]` to `🟠 ERROR` (emoji badge). Any consumer or CI pipeline parsing the text output will break. The plan explicitly said "No breaking changes" but this changes observable output without a feature flag or backward-compatible mode.

**Affected:** Any consumer using `FormatText` for machine-parseable output. The CLI tool `go-finding` uses this for its `-format text` output.

**Fix options:**

1. Add `FormatTextClassic()` for the old format, make `FormatText` the new enriched one
2. Revert `FormatText` to old format, add `FormatTextRich()` for the new format
3. Keep as-is and document it as a breaking change in v1.3.0 migration notes

### D2: `Finding.IsValid()` semantic change

**Severity: MEDIUM**

Changed from `Position.IsValid()` (requires File + Line > 0) to `Position.HasFile()` (requires File only). This means findings with `Position{File: "x", Line: 0}` now return `IsValid()=true` where they previously returned `false`. Any consumer relying on `IsValid()` to filter out file-level findings will be affected.

This was the intended design (M4 root-cause fix), but it IS a behavioral change to a public API method, not purely additive.

### D3: `FindingTemplate` name stutters

**Severity: LOW (lint)**

revive flags: `finding.FindingTemplate` stutters. Should be `finding.Template`. The plan named it `FindingTemplate` but the revive linter in this project flags package-name-stuttering. Renaming to `Template` would be `finding.Template` which reads better.
