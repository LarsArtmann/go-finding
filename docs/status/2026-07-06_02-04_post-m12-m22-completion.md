## e) WHAT WE SHOULD IMPROVE

### Architecture

1. **Position.File is FilePath but Range doesn't enforce same-file** — `Range.Start.File` and `Range.End.File` can differ with no validation. A `NewRange` that validates same-file would make invalid ranges unrepresentable.
2. **SARIF deprecated APIs accumulate** — `ToSARIFFiltered`, `WriteSARIFFiltered` are deprecated but still present. Need a deprecation strategy (v1.1 removal? build tag?).
3. **LSPDiagnosticData is go-finding-specific** — The Data field pollutes the LSP type with go-finding concerns. Consider a separate `LSPOptions` type for clean separation.
4. **Analysis BeforeCode reads from disk** — This is a filesystem dependency in what should be a pure conversion. A `FromDiagnosticWithSource(d, fset, source, ...)` variant would be cleaner.

### Type Safety

5. **Severity still uses string comparisons** — Could use an int-backed enum with string rendering for better performance and exhaustiveness.
6. **Confidence has no sentinel for "unset"** — Zero value means 0.0 which is a valid confidence. `OffsetUnknown` pattern should be applied.
7. **FixStrategy is a string type** — Could be an int enum with typed constants for compile-time exhaustiveness in switches.

### Testing

8. **No fuzz tests for LSP round-trip** — SARIF has fuzz tests, LSP doesn't.
9. **No CLI binary integration tests** — We test packages but never run the actual binary.
10. **Benchmark coverage is thin** — No benchmarks for SARIF import/export, LSP conversion, or FilePath operations.

### Process

11. **Commit granularity** — Should commit per-task, not per-batch. The 5-task mega-commit was too large.
12. **No `CHANGELOG.md`** — Breaking changes (FilePath type) and new features (SARIFOption) should be tracked.
13. **No version bump** — We added breaking changes without bumping version or tagging.

## g) Top #1 Question

**Should we remove the deprecated `ToSARIFFiltered` and `WriteSARIFFiltered` before tagging v1.0.0, or keep them as deprecated aliases for backward compatibility?**

The new `ToSARIFWithOpts(WithMinSeverity(sev))` fully replaces them. But removing them is a breaking change for any consumer that calls `ToSARIFFiltered` directly. Since we haven't tagged v1.0 yet, this is our last chance to clean the API surface. If we keep them, they accumulate as maintenance burden forever.

**My recommendation:** Remove them. v1.0 is the clean break. But I need your call because I don't know if any of the 20 audited consumers depend on these specific method names.
