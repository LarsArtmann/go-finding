### 1. LineShiftMap pipeline integration
- **What's done:** LineShiftMap constructed in `applyToFile`, returned via `ApplyWithShiftMap`, wired into `applyTriage` to shift `iter.findings` line numbers after fix application.
- **What's partial:** Only shifts `Position.Line` — does not shift `Range.Start.Line`/`Range.End.Line` or `Position.Column`. The Range fields on findings in the iteration are not updated.
- **Impact:** Low — most post-fix findings don't have Ranges, and column numbers rarely shift from line-level edits.

### 2. Correlate IntervalIndex integration
- **What's done:** Three correlation strategies implemented: range-overlap (IntervalIndex), line-proximity (existing), and cross (point-within-range). All tested.
- **What's partial:** Not benchmarked against the old O(n²) approach. For small-to-medium datasets, the overhead of building the IntervalIndex may exceed the O(n²) scan cost.
- **Impact:** Low — correctness is proven by tests; performance is equal or better for large datasets.

## G) Top #1 Question I Cannot Figure Out Myself

**What are the Position/Range zero-value semantics decisions, and when is v1.0.0?**

Three breaking-change decisions block v1.0 API stability:

1. **Position.Offset=0** — Is byte offset 0 "valid" (byte 0 of file) or "unset" (zero value)? Currently it's both — `IsZero()` and `HasOffset()` both return `true`. This is a semantic trap.
2. **Range.End zero value** — Does `Range.End.Line == 0` mean "same as Start" or "not set"? Currently `HasEnd()` checks `End.Line > 0`, making 0 mean "unset". But some consumers might expect 0 to mean "end of line 0" (i.e., the first line).
3. **PositionOffset sentinel** — Should we use `-1` as "not set" sentinel for Offset (breaking change from current 0), or introduce a separate boolean field, or use a pointer?

These are purely design decisions with no technical blocking issue. But they determine whether v1.0 can be released with a stable API or needs another breaking minor version first.
