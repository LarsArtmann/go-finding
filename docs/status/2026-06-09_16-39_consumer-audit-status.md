## Executive Summary

## e) WHAT WE SHOULD IMPROVE

### High Impact — Based on Consumer Audit Evidence

1. **Severity mapping is the #1 pain point** — 7 projects, each with a 5-15 line switch statement. `ParseSeverity` needs alias expansion (1 afternoon fix, eliminates 100+ lines of duplication).

2. **The `pipeline` package is scaring away consumers** — 12/15 projects don't use it, but it's the most complex part of the library. Extracting it would make the core package 40% smaller and far more approachable.

3. **Detector interface in wrong package** — `pipeline.Detector` is the universal interface every consumer implements, but importing it pulls in FixEngine, FixApplier, Metrics, etc. Move to root.

4. **No tool adapter helper** — ~30 files across 5 projects implement the same JSON→Finding pattern. A generic `ToolAdapter[O any]` would eliminate 60% of this code.

5. **Category knowledge is tribal** — "errcheck is Security, revive is Style" lives in 3 separate codebases. Centralize it.

### Medium Impact

6. **Dead API ships in every binary** — Suppression (0 consumers), filter combinators (0 consumers), SARIF import (0 consumers), Severity.Badge/Emoji (0 consumers). Remove pre-v1.0.

7. **`Report.Findings` encapsulation** — ADR 10 acknowledges the risk but punts. `FindingsSnapshot()` exists but nobody uses it. Need migration plan.

8. **Confidence is underutilized** — Only branching-flow (5) and hierarchical-errors (1) set it. Either promote or simplify.

9. **BeforeCode/Related fields are dead** — 2 and 0 consumers respectively. Consider removal pre-v1.0.

### Lower Impact

10. **Race detector on FixApplier single-use** — Document or guard with mutex.
11. **Benchmark coverage** — Only fix_engine has benchmarks. Pipeline, merge, diff, filter all lack perf baselines.
12. **External documentation** — README doesn't reflect consumer-audit insights. No "how to migrate from hand-rolled findings" guide.

## g) Top #1 Question I Cannot Figure Out Myself

**Should the `pipeline` package be extracted to a separate Go module (`go-finding-pipeline`), or should we keep it as a sub-package but make it `//go:debug`-gated behind a build tag?**

The evidence is clear: 12/15 consumers don't use pipeline, and the 3 that do only use `Detector` interface + `Config` + basic `Run()`. The FixEngine, FixApplier, Conflict detection, Retry, Metrics, Verification, GeneratedFileFilter, and FileBackup subsystems have zero external consumers. However, the pipeline is used extensively by `cmd/go-finding` internally and by oxlint-auto-configure externally.

The question is: **does extracting it add more value (leaner core, independent versioning, clearer API surface) than it costs (two repos to maintain, cross-module CI, consumer migration)?** This is a product/ownership decision I cannot make.
