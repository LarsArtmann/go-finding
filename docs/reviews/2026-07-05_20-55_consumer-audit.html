02Consumer tiers

Tier 1: Deep integration (Pipeline + Detector + Types)

go-structure-linter — The exemplar consumer. Type aliases (type Issue = finding.Finding) eliminate all conversion boilerplate. Full pipeline with custom TriageFunc, FindingTransformer, StageHook bridge. Uses finding.Pos() across 65+ call sites. This is the gold-standard integration pattern.

Tier 1: Deep integration

oxlint-auto-configure — Full pipeline with RetryConfig, Metrics, OnFinding/OnIteration callbacks, Combine+Dedup. Implements finding.Detector. Uses structured errors (NewIOError, NewParseError). Cleanest pipeline wiring.

03Recurring usage patterns

The type-alias pattern (gold standard)

Used by go-structure-linter and template-CLI:

type Issue = finding.Finding
type Severity = finding.Severity
type RuleCategory = finding.Category

This eliminates all conversion boilerplate. Rules produce finding.Finding directly via finding.Pos(). No wrapping, no mapping. This should be the documented recommended pattern.

The converter/violation pattern

Used by branching-flow (12 converter files), BuildFlow, Code-Quality-Agent:

Domain violation types → []finding.Finding via per-type converter functions. Each converter repeats severity/category/confidence mapping. Branching-flow's NewViolationBuilder centralizes this; CQA doesn't (inconsistent).

The Detector-standalone pattern

Used by template-LICENSE, go-functional-fixer, golangci-lint-auto-configure:

Implements finding.Detector for composability, with DetectReport(ctx) (*Report, error) as a standalone entry point. Good for plug-in architecture, but two of three never actually wire a pipeline.

Severity mapping: everyone reinvents it

Every multi-detector consumer (branching-flow, BuildFlow, CQA, go-auto-upgrade, library-policy) has its own MapSeverity() function mapping domain severity strings to finding.Severity. This is pure boilerplate that go-finding could provide as a configurable helper or registry.

04Issues found in consumers

Critical · Compile-breaking

3 templates access the unexported Report.findings field

template-AUTHORS main.go:146 · template-SECURITY security_validator.go:52, validate.go:176 · template-readme core_functions.go:160

These access report.Findings directly, but at v1.0.0 the field is unexported (findings). Either these projects don't compile against the actual published v1.0.0 tag, or they depend on a pre-release where the field was public. They should use FindingsSnapshot() or ActiveFindings().

Action for go-finding: This is an API migration pain point. Consider a deprecation guide or a compatibility shim. Also: is the field truly unexported at the tagged v1.0.0? Verify the release.
Important · Reinvention

BuildFlow reinvents the FixEngine with manual BeforeCode/AfterCode replacement

BuildFlow modules/checker-helpers/helpers.go:190 (ApplyTextFixes)

BuildFlow reads f.FixStrategy == FixStrategyDirect + f.BeforeCode + f.AfterCode and performs manual strings.Replace. This is exactly what go-finding's FixEngine/FixApplier provides. The consumer either doesn't know the FixEngine exists, or it doesn't meet their needs.

Action for go-finding: Document the FixEngine better. If it doesn't meet real-world needs (e.g. BuildFlow needs file-system-aware multi-file fixes), understand the gap and close it.
Important · API misuse

Code-Quality-Agent + library-policy skip the Builder entirely

CQA: all 6 adapters · library-policy: types.go:131-142

These use NewFinding() then directly mutate fields (f.Category = ..., f.Metadata = ...), bypassing the Builder's validation. CQA also passes raw strings for RuleName/ToolName, defeating the branded-type safety. CQA hardcodes Confidence: 1.0 across all adapters.

Important · Dead interface impl

2 projects implement Detector but never wire a pipeline

go-functional-fixer (detector.go:11) · golangci-lint-auto-configure (detector.go:16)

The Detector implementation exists for pipeline-readiness but is never used with pipeline.New() + Run(). This suggests the pipeline integration story isn't clear enough, or the pipeline doesn't meet their orchestration needs.

Important · Bug

go-functional-fixer: Range end-line always equals start-line

go-functional-fixer pkg/analyzer/finding_adapter.go:19,29

endLine is set to the same value as lineNum, so multi-line ranges are structurally created but never span multiple lines. A real consumer bug, but also reveals that go-finding's Range API doesn't prevent this footgun.

Important · Dependency hygiene

library-policy on local replace; template-readme mislabeled indirect

library-policy go.mod:94 · template-readme go.mod:38

library-policy uses replace ... => /home/lars/projects/go-finding with version v0.0.0-00010101000000-000000000000 — not publishable. template-readme has 7 direct imports but marks go-finding // indirect.

Low · Inconsistency

Inconsistent Detector interface source & construction patterns

Across all 9 Detector implementors

2 use pipeline.Detector (type alias), 4 use finding.Detector (canonical). 4 use NewFinding(), 5 use NewBuilder(), 2 alias the types. NewBuilder() + .Build() is the recommended modern path with validation, but only 5 of 15 consumers use it. Only template-LICENSE has a compile-time assertion (var _ finding.Detector = (*X)(nil)).

05Implications for go-finding

What real-world usage tells us go-finding should improve.

1. Nobody uses FindingsFromSARIF (SARIF import)

All 15 consumers use SARIF as output only. Not a single consumer parses SARIF to import findings. The SARIF import path (with its silent data-loss bugs found in the code review) is completely untested by real usage. This is either a YAGNI feature, or it needs promotion / documentation / integration examples.

2. Only 3 of 15 use the Pipeline

The pipeline is go-finding's flagship feature (detect→triage→fix→verify), but only go-structure-linter, oxlint-auto-configure, and template-AUTHORS actually use it. The other 12 have their own orchestration. This suggests either the pipeline is too opinionated, too hard to adopt incrementally, or consumers don't know it exists. Action: Document a migration path from "just types" to "full pipeline."

3. Provide a shared Severity mapper

Every multi-detector consumer reinvents MapSeverity(string) finding.Severity. This is pure boilerplate. A configurable mapper or registry (similar to the existing RegisterSeverityAlias) would eliminate this across 5+ projects.

4. FixEngine discoverability gap

BuildFlow reinvents FixEngine functionality with manual text replacement. Either the FixEngine isn't discoverable, or it doesn't meet real multi-file fix needs. Action: Document FixEngine usage with a real-world example. Investigate why BuildFlow couldn't use it.

5. The Report.findings unexporting broke consumers

At least 3 template projects access report.Findings which is now unexported. The migration path (FindingsSnapshot() / ActiveFindings()) exists but isn't obvious. Action: Add a migration note to docs/MIGRATION_v1.0.md and verify these consumers compile.

6. The type-alias pattern should be the documented default

go-structure-linter's pattern (type Issue = finding.Finding) eliminates all conversion boilerplate and is the cleanest integration. Action: Add this to the README as the recommended integration pattern, with a before/after example.

7. The Builder pattern works — promote it

Consumers using NewBuilder() + .Build() have fewer bugs than those using NewFinding() + field mutation. template-LICENSE's compile-time assertion pattern should be documented. Action: Deprecation-path NewFinding or add a lint rule.

8. Advanced features (RelatedRef, Suppression) are barely used

Only hierarchical-errors uses RelatedRef, Suppression, ActiveFindings(), and the analysis subpackage. These features work and are correctly designed, but adoption is minimal. This validates their existence (at least one sophisticated consumer needs them) but suggests the docs should showcase them.

9. Fix the dependency tree metadata

projects-management-automation and go-wizard-sdk are listed as indirect consumers but have zero go-finding presence. The dependency graph data is stale.

06Deep dives — notable consumers

go-structure-linter — the exemplar

Why it's the gold standard: Type aliases (type Issue = finding.Finding) mean the linter's entire rule system produces go-finding types directly — zero conversion boilerplate. Full pipeline integration with custom TriageFunc, FindingTransformer (severity filter), StageHook bridge to event system. The SDK exposes LintWithPipeline(), FixWithPipeline(), GetMetrics(). 65+ finding.Pos() call sites. This is the integration pattern go-finding should document and promote.

BuildFlow — the deepest core consumer

Uses Combine + WithDeduplication + DeduplicateByID + SortFindingsByID + Diff + GenerateID — the most advanced merge/diff usage. Wraps *finding.Report in its own FindingSummary model, creating a two-layer architecture. Reinvents FixEngine via manual BeforeCode/AfterCode replacement (the biggest reinvention gap). Has its own Detector/Repairer/Generator interfaces that are conceptually parallel to go-finding's but not compatible.

hierarchical-errors — the advanced-feature consumer

The only consumer using RelatedRef (parent-child error hierarchy for SARIF), Suppression (//nolint handling), ActiveFindings() (correct SARIF suppression semantics), analysis.FromTokenPosition() (the analysis subpackage), and Finding.Key() for deduplication. Uses namespaced metadata keys following go-finding's convention. Validates that advanced features work correctly for at least one real consumer.

Code-Quality-Agent — the anti-pattern

Uses NewFinding() + direct field mutation everywhere (no Builder), raw strings for branded types (defeats type safety), hardcoded Confidence: 1.0 across all adapters, inconsistent category assignment per adapter. Also has its own Adapter interface that's conceptually parallel to finding.Detector but doesn't implement it. Has a health score that manually counts severities instead of using report.Summary.BySeverity (which is already computed). This consumer would benefit most from go-finding API guidance.
