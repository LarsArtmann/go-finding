go-finding — Type System Audit

00Summary

The model is honest and well-documented — every "gotcha" is called out in AGENTS.md and field doc-comments. That said, the Finding struct mixes six conceptual responsibilities (identity, location, classification, fix, context, extensibility) into one flat shape, and several named types still encode optional state through pointers or asymmetric sentinels. None of these are blocking for v1.0, but two — the Position sentinel split-brain and FixStrategy zero-value normalization — will keep biting consumers until they are type-level invariants rather than runtime conventions.

The bottom line Adopt branded primitive types (Rule, ToolName, FilePath, FindingID) before v1.0 — cheap, breaking-once, prevents a class of mixups forever. Defer the FixStrategy interface-union and Position redesign to v2.0; document them as known type-level debt.

◆What's already excellent

Before cataloging problems: the model is unusually disciplined for an organically-grown Go library. Several design choices are exactly right.

+
Named types everywhere a concept matters Severity, Category, Confidence, FixStrategy, Tag, SuppressionKind, RelationKind are all named — not raw strings. Confidence even has Clamp() + IsValid().
+
Single extensibility escape hatch, intentionally restricted Metadata map[string]string (NOT map[string]any). Documented in finding.go:36-46 with a key-namespacing convention. Lossless for SARIF/JSON interchange.
+
Structured errors with errors.Is support FindingError implements Is()/Unwrap(), has an ErrorCategory enum, and five sentinel roots. Composes with errors.Join in Validate().
+
Builder enforces invariants at construction Builder.Build() validates and normalizes (FixStrategy "" → "none", clamps Confidence). Consumers who use the Builder get guaranteed-valid findings.
+
Generics where they pay off IntervalIndex[T] for O(log n + k) overlap queries. ToolAdapter[O any] for tool-output-agnostic adapters. No premature genericization of simple types.

01Problem Catalog

Seventeen issues across six categories, ordered by severity × systemicity.

Blocking · Type-level bug magnet

P1 — Position has three different sentinel conventions

position.go:23-29 · cascades into Range, Finding, RelatedRef

Line/Column use 0 = "not set" (1-based). Offset uses -1 = "not set" (0-based, so 0 IS valid). The zero value Position{} therefore has Offset=0 (a valid byte position!) but File="" (invalid). Position{}.IsZero() returns false. Every consumer must remember to call HasOffset() rather than Offset > 0. Three conventions in four fields. 

// Position{} has Offset=0 (valid byte!) but no file.
// IsZero() returns false. HasLocation() returns false.
// IsValid() returns false (File is empty).
// Three predicates, three answers about the same value.
p := finding.Position{}
p.IsZero()     // false
p.HasOffset()  // true
p.IsValid()    // false
Fix (v2.0, breaking) Use *int (nil = unset) for all three numeric fields, OR adopt a single type Option[T any] struct{ V T; Ok bool } helper. This collapses three conventions to one and makes Position{} mean "unset everywhere".
Important · Split-brain that NormalizeFixStrategy papers over

P2 — FixStrategy "" vs "none" is a runtime convention, not a type invariant

Per-finding resolution (annotated 2026-09-08): ✅ Resolved: NormalizeFixStrategy() converts "" to "none" (Builder, SARIF import, Equal short-circuit) — the convention became code.

fix_strategy.go:50-56 · called from Validate, Builder.Build, FromLSP, SARIF import

The zero value FixStrategy("") is invalid; consumers must call NormalizeFixStrategy to convert it to "none". Four entry points do this manually. A fifth entry point — direct struct literal construction — silently produces invalid findings. The existence of NormalizeFixStrategy is itself the smell: it is runtime correction for what should be a type-level invariant.

Fix (v2.0, breaking) Redesign FixStrategy as an interface-based closed union: type Fix interface{ fixStrategy() } with NoFix, Suggestion{Text string}, Direct{Before, After string}, AIReserved — each constructor validates its own invariants. The "Direct requires BeforeCode" rule becomes a constructor check, not a Validate() clause.
Important · High systemicity

P3 — Primitive obsession: Rule, ToolName, File, Message, ID are raw strings

Per-finding resolution (annotated 2026-09-08): ✅ Resolved v1.1.0: branded types ID/RuleName/ToolName/FilePath (+GroupID v1.7.0) in branded_types.go.

finding.go:10-47 · 6 distinct domain concepts share the same type

All six are string. Nothing prevents f.Rule = f.ToolName or ref.FindingID = "some random text". They are conceptually distinct and never interchangeable — exactly the case branded types exist for. 

// Current — all interchangeable at compile time
type Finding struct {
    ID       string // really a FindingID
    Rule     string // really a RuleName
    ToolName string // really a ToolName
    Message  string // really a HumanMessage
    Position Position // File is really a FilePath
}
Fix (v1.0, cheap — DO THIS) Add branded types: type FindingID string, type RuleName string, type ToolName string, type FilePath string. JSON tags stay identical (branded string marshals as string). Compile-time mixup prevention; zero runtime cost; one-time breaking change before the v1.0 API lock.
Important · Five sites

P4 — Pointer fields encode optional state implicitly

Per-finding resolution (annotated 2026-09-08): 🔵 Parked for v2.0 by design: pointer-as-state (Range, Suppression, ExpiresAt) — ROADMAP 'Hardening (owner decisions pending)'.

finding.go:29-33 · suppression.go:20 · errors.go:44-48

Five pointer fields encode three states (nil / zero / valid): Range *Range, Suppression *Suppression, Suppression.ExpiresAt *time.Time, RelatedRef.Range *Range, FindingError.Finding *Finding. Each is a potential nil-dereference site and forces defensive checks throughout.

Fix (mixed — some v1.0, some v2.0) v1.0: Keep pointers but document nil-semantics per field (most are already documented). v2.0: Replace *time.Time with ExpiresAt time.Time + HasExpiry bool; replace *Range on Finding with Range + HasRange bool (Range already has IsValid()).
Important · Concurrency footgun

P5 — SeverityAliases is a mutable global map

Per-finding resolution (annotated 2026-09-08): ✅ Resolved: SeverityAliases global removed; RWMutex-guarded Register/Lookup API.

severity.go:181-191 · consumed by ParseSeverity

var SeverityAliases = map[string]Severity{...} is a package-level mutable map. The doc-comment invites mutation ("Consumers can add custom aliases via this map before calling ParseSeverity"). Concurrent read-after-write on a Go map is a runtime panic. Library consumers who customize aliases cannot do so safely.

Fix (v1.0, low risk) Replace with a func RegisterSeverityAlias(name string, sev Severity) guarded by a sync.RWMutex. Or accept aliases as a parameter to a new ParseSeverityWithAliases(s, aliases). Either way, kill the global mutable map.
Nice to have · Readability

P6 — Finding is a 17-field flat struct mixing six concerns

Per-finding resolution (annotated 2026-09-08): 🔵 Parked for v2.0 by design: Finding sub-struct composition (Identity/Location/Classification/Fix) — changes JSON shape, must batch.

finding.go:8-48 · identity / location / classification / fix / context / extensibility

The field-grouping comments help, but the compiler doesn't enforce them. Composition via embedded structs (Identity, Location, Classification, Fix) would let consumers pass sub-structs to focused functions.

Decision: DEFER to v2.0 Listed in TODO_LIST.md as "DEFERRED v2 (breaking change)". Composition changes JSON serialization shape — must be batched with other v2.0 breaks.
Nice to have · Type safety

P7 — RelatedRef.FindingID is raw string, not branded FindingID

Per-finding resolution (annotated 2026-09-08): ✅ Resolved v1.1.0: RelatedRef.FindingID is the branded ID type.

finding.go:83 · Correlation.FindingIDs []string

Once FindingID is a branded type (issue P3), RelatedRef.FindingID and Correlation.FindingIDs should use it. This makes it impossible to put a rule name where a finding ID belongs.

Nice to have · Semantic clarity

P8 — Tags []Tag is a slice, not a set

Per-finding resolution (annotated 2026-09-08): 🔵 Parked for v2.0 by design: Tags → TagSet (order-insensitive Equal fast path mitigates in v1.x).

finding.go:21 · order-sensitive equality via finding_equal.go

Conceptually Tags is a set (no semantic meaning to order, duplicates are noise). It's a slice. finding_equal.go must therefore do order-insensitive comparison. Constructors don't dedup. A type TagSet map[Tag]struct{} would encode the invariant at the type level.

02Target model (sketch)

The redesign is staged: cheap branded types land in v1.0, structural changes wait for v2.0. The sketch below shows the target end-state. 

// v1.0 — branded primitive types (no struct shape change)
type (
    FindingID string
    RuleName  string
    ToolName  string
    FilePath  string
)

type Finding struct {
    ID       FindingID `json:"id"`
    Rule     RuleName  `json:"rule"`
    ToolName ToolName `json:"toolName"`
    // ... Message stays string (human text, not identity)
    Position Position  // Position.File becomes FilePath
}

// v2.0 — FixStrategy as closed interface union
type Fix interface { isFix() }

type NoFix struct{}                   func (NoFix) isFix() {}
type Suggestion struct{ Text string } func (Suggestion) isFix() {}
type Direct struct {
    Before string // required
    After  string // required
}                          func (Direct) isFix() {}
type AIReserved struct{}            func (AIReserved) isFix() {}

// "Direct requires Before/After" becomes a constructor invariant:
func NewDirect(before, after string) (Direct, error) {
    if before == "" && after == "" {
        return Direct{}, ErrValidation
    }
    return Direct{before, after}, nil
}

// v2.0 — Position with one sentinel convention
type Position struct {
    File   FilePath
    Line   Option[int] // absent for "unset"
    Column Option[int]
    Offset Option[int] // no more -1 sentinel
}
Why this state is better Three sentinel conventions collapse to one (Option[T]). The "Direct requires code" rule becomes unrepresentable-as-invalid at construction. FindingID mixups become compile errors. SeverityAliases mutation becomes safe.

Decision log

Decision Choice Rejected alternative
v1.0 branded primitives Do it — cheap, one-time break Keep raw string — accept forever mixups
v1.0 SeverityAliases mutex Wrap in sync.RWMutex Freeze as immutable — loses extensibility
v2.0 Fix union Closed interface with private tag method Generics — Go interfaces can't combine with type params cleanly here
v2.0 Position Option[T] Generic Option[T] struct *int — escapes to heap, nil-deref risk remains
v2.0 Finding composition Embed Identity, Location, Fix Keep flat — conflicts with Focus-on-substruct API ergonomics
