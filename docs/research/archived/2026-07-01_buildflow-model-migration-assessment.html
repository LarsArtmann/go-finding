📦 Resolution Status (updated 2026-07-16): This is a historical research assessment. go-finding's Finding model was adopted as the basis for BuildFlow's detection pipeline. The multi-module structure proposed here was implemented and shipped in v1.1.0.

Migration Assessment — BuildFlow/model/ → go-finding

Date: 2026-07-01 Analyst: Crush Question: Should any types from BuildFlow/model/ be migrated to go-finding?

Full read-through of every file in BuildFlow/model/ compared against go-finding's core types and pipeline/ package. Verdict: no migration.

Verdict: No Migration

Every type in BuildFlow/model/ is application-level build orchestration policy. go-finding is a static analysis library. The dependency direction is already correct (BuildFlow imports go-finding, not vice versa). Migrating anything upstream would pollute the library with application concerns, violate the "minimal dependencies" design principle, and create a circular conceptual dependency.

1. BuildFlow/model/ Inventory

Every file in BuildFlow/model/ was read. They group into five categories:

1.1 Build Pipeline Config & Flags

  • config.go — Config struct with Validate(): build mode, language, tool paths, max concurrency, file size limits, duplication thresholds
  • config_substructs.go — ExecutionControl, OutputSettings, ValidationSettings, GoToolchainConfig embedded into Config
  • build_flags.go — BuildFlags: TrimPath, StripSymbolTable, StripDWARF, Race, LDFlags, Tags
  • runtime_flags.go — RuntimeFlags: GCTrace, SchedTrace, GOTRACEBACK, GOMAXPROCS, GOGC, GOMEMLIMIT
  • test_flags.go — TestFlags + FuzzTestFlags: Shuffle, Timeout, Count, CoverMode, CoverProfile, FuzzTime

Verdict: Application-specific

These are BuildFlow's CI execution configuration — how to compile, test, and run Go projects. They control go build, go test, and runtime behavior. None of this belongs in a static analysis finding library.

1.2 Violation Types & Interface

  • base_violation.go — Violation base struct (File, Line, Column, Pattern, Reason, Severity, ViolationType) + interface methods
  • violation_interface.go — PrioritizedViolation interface (GetFile, GetSeverity, GetViolationType, GetPriorityValue, GetMessage, GetLine, GetColumn)
  • violation_type.go — ViolationType int enum (Compilation, Runtime, Security, Duplication, Binary, Size, Style, TODO, Linter, Dependency, DocsAge) + DefaultSeverity()
  • code_violations.go — BinaryViolation (embedded Violation + Size)
  • docs_violations.go — AgentsMdExistsViolation
  • quality_violations.go — FileSizeViolation (LineCount, MaxAllowed)
  • violation_sort.go — CompareViolations, SortViolations[T] (priority → file → line → column)

Verdict: Parallel abstraction, already subsumed by go-finding

Violation is a strictly simpler version of finding.Finding. ViolationType overlaps with finding.Category. SortViolations duplicates what Severity.Compare() + standard sort already provides. These are BuildFlow's own policy types that happen to reuse finding.Severity — they are not more general than what go-finding already offers.

1.3 Build-Step Results & Metadata

  • step_result.go — StepResult (Step, Status, Duration, Message, Error, Report, Metadata) + StepDiagnostics (CommandOutput, Command)
  • step_metadata.go — StepMetadata (Violations, ToolCapabilities, FilesScanned, TotalFiles, FilesFiltered, DirectoriesExcluded, ModulesProcessed, RepairMetadata, Extra map)
  • step_metadata_builder.go — StepMetadataBuilder fluent API
  • step_metadata_json.go — Custom MarshalJSON/UnmarshalJSON for flat JSON backward compatibility
  • capability_info.go — CapabilityInfo (SupportsAutoFix, FixCapability, SupportsDryRun)
  • repair_metadata.go — RepairMetadata, FixSummary, GolangciMigrateResult, ProjectFixResult, DiskSpaceAutoFixResult, AutoFixStatus, MigrateStatus
  • finding_report.go — FindingSummary (ToolName, FindingCount, SeverityCounts, Original *finding.Report)

Verdict: BuildFlow execution engine concerns

StepResult tracks whether a build step (compile, test, lint) passed/failed/skipped. StepMetadata aggregates execution stats. RepairMetadata encodes BuildFlow-specific repair tools (go-structure-linter, golangci-lint migrator, projectfix, disk-space cleanup). CapabilityInfo describes whether a BuildFlow tool supports auto-fix or dry-run. None of these concepts exist in or belong to a static analysis library.

1.4 Validation Result Container

  • result.go — ValidationResult[T PrioritizedViolation] generic container with ErrorCount/WarningCount/InfoCount, Duration, Validate(), IsSuccess(), custom JSON
  • result_helpers.go — GetFilesWithViolations(), GetViolationsByFile(), GetMostSevereViolation()
  • result_filters.go — FilteredBySeverity(), FilteredByType(), FilteredByFile()

Verdict: BuildFlow-specific aggregation

ValidationResult[T] is a violation aggregation container for BuildFlow's specific violation types. It is constrained to PrioritizedViolation (a BuildFlow interface). go-finding already has Report with Summary (BySeverity, ByCategory, ByFixStrategy, FilesAffected) that serves the same purpose at the library level.

1.5 Errors, Misc

  • errors.go — SerializableError, DependencyError with hardcoded toolInstallCommands map (golangci-lint, art-dupl, sqlc, goimports, etc.)
  • git_todo.go — LineColumn type alias to finding.Position, GitCheckOptions, GitCheckResult, SourcePosition
  • severity.go — SeverityPriority() function mapping finding.Severity → int for sorting
  • metadata_keys.go — MetadataKey branded string type + constants for go-mod and pnpm update keys

Verdict: BuildFlow-specific

errors.go hardcodes BuildFlow toolchain knowledge. metadata_keys.go encodes BuildFlow module/npm operations. severity.go duplicates finding.Severity.Compare(). git_todo.go mixes git-check options with a position alias.

4. Pipeline Comparison

The most likely migration target is pipeline/, since both deal with "running analysis." However, they solve fundamentally different problems:

Dimension go-finding pipeline/ BuildFlow model/
Purpose Iterative detect → triage → fix → verify loop for automated remediation Build orchestration — track pass/fail/status of CI steps (compile, test, lint, format, dependency check)
Core result PipelineResult — iterations, fixes applied, correlations, completion reason StepResult — one step's status, duration, error, findings summary
Granularity Finds and fixes individual code issues at specific source locations Tracks whether a build step completed successfully
Config MaxIterations, Timeout, FixProviders, Retry, TriageFunc, StageHooks BuildMode, ToolPaths, GoToolchainFlags, FileSizeLimits, DuplThreshold
Metrics Per-detector timing, fixes applied, stage durations Files scanned, modules processed, repair summaries
Relationship BuildFlow is the caller. It could use go-finding's Pipeline to run detectors internally, but its model types encode CI orchestration concerns that don't belong in a static analysis library.

5. Architectural Argument

Dependency Direction

BuildFlow already imports go-finding (import "github.com/larsartmann/go-finding"). The Violation base struct uses finding.Severity. The ValidationResult counts violations by finding.SeverityCritical, finding.SeverityError, etc. FindingSummary holds Original *finding.Report. LineColumn is aliased to finding.Position.

Migrating any of these types upstream would invert the dependency for no benefit — it would make go-finding depend on concepts that only BuildFlow needs, while BuildFlow would still need its own wrappers for its application-specific policy.

Library vs Application Boundary

go-finding's design principle #1 is "minimal dependencies — core types depend only on stdlib." Every type in BuildFlow/model/ either:

  • Encodes application policy (which tools to install, what file sizes to enforce, which violation types exist)
  • Depends on BuildFlow-specific packages (buildflow/domain, buildflow/constants, buildflow/modules/errors, buildflow/logger)
  • Hardcodes toolchain knowledge (golangci-lint, art-dupl, sqlc, ginkgo, etc.)

Bringing any of this into go-finding would violate the library's dependency-free core principle and import application concerns into a library that other consumers expect to be clean.

The "Superset" Test

For each overlap area, go-finding already provides the more general abstraction:

  • Finding (16+ fields, builder, validation, JSON, SARIF, LSP) ⊃ Violation (7 fields, no serialization)
  • Category (16 standard + arbitrary custom, parse/validate) ⊃ ViolationType (11 fixed int constants)
  • Report + Summary (thread-safe, BySeverity/ByCategory/ByFixStrategy) ⊃ ValidationResult[T] (ErrorCount/WarningCount/InfoCount)
  • Severity.Compare() (total ordering, invalid handling) ⊃ SeverityPriority() (simple int mapping)

The migration direction would need to be the opposite — BuildFlow adopting go-finding types more directly — for there to be any value. But even that is a BuildFlow refactor, not a go-finding change.

6. Candidates Considered and Rejected

Candidate: ViolationType.DefaultSeverity() mapping

Why considered: Maps violation categories to default severity — could be useful as a general "category → default severity" concept.

Why rejected: The mapping is BuildFlow policy (compilation→critical, docs-age→warning, binary→error). go-finding's Category intentionally does NOT prescribe severity — that's a tool-specific decision. Adding default severities would impose opinions the library deliberately avoids.

Candidate: CapabilityInfo (auto-fix / dry-run support)

Why considered: Describes tool capabilities — seems like it could pair with FixStrategy.

Why rejected: go-finding already encodes fix capability per-finding via FixStrategy (none/suggest/direct/ai) and HasFix() / IsAutoFixable(). CapabilityInfo describes whether a tool supports a CLI flag (--fix, --dry-run) — that's BuildFlow's execution concern, not a per-finding property.

Candidate: CompareViolations / SortViolations[T]

Why considered: Canonical sorting of violations by priority → file → line → column.

Why rejected: Generic sort on Finding can trivially be done with slices.SortFunc and existing Severity.Compare() / Position.Compare(). The priority formula (severityRank * 1000) + violationType is specific to ViolationType, which is BuildFlow-only. Adding a sorting utility for a type the library doesn't use adds dead code.

Candidate: SerializableError

Why considered: Structured error for JSON serialization — seems generic.

Why rejected: go-finding already has FindingError with Category, Finding, Message, Cause, File, Position — far richer and domain-specific. SerializableError embeds BuildFlow's error classification (BuildFlowError, go-error-family Classified) which go-finding doesn't use.

7. Future Direction: What BuildFlow Should Do Instead

Instead of migrating types to go-finding, BuildFlow should consider adopting go-finding's existing types more directly:

Current BuildFlow pattern Could adopt from go-finding Benefit
Violation base struct (7 fields) finding.Finding (16+ fields with builder, validation, SARIF, LSP) Richer data model, free SARIF/LSP export, no parallel hierarchy
ValidationResult[T] container finding.Report + Summary Thread-safe, category breakdown, built-in aggregation
SeverityPriority() + SortViolations[T] Severity.Compare() + slices.SortFunc Eliminate duplicate ordering logic
ViolationType enum finding.Category (custom categories allowed) Use CategoryCorrectness, CategoryStyle, CategoryDuplication, plus custom categories for Binary/Size/DocsAge

This is a BuildFlow refactor — it changes BuildFlow's code, not go-finding's. go-finding already has everything needed. No migration is required for this direction; it's an adoption question on the consumer side.

Final Verdict

No migration from BuildFlow/model/ to go-finding. Every type is either application-specific build orchestration policy or a strictly simpler duplicate of an existing go-finding abstraction. The dependency direction is correct (BuildFlow → go-finding). go-finding's library boundary and dependency-free core principle must be preserved.
