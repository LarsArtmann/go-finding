00 — Executive Verdict

Well-designed library, narrow fit for go-finding

Overall assessment: 7.5 / 10 as a library; 5 / 10 as a go-finding dependency

go-error-family is a thoughtful, well-executed library. Its protocol of small interfaces (Coded, Classified, Contextual, Retryable) is the right abstraction for behavioral error handling at CLI/HTTP boundaries. The code is clean, tested, lint-free, and documented.

For go-finding, however, the value is limited. The library's Families, diagnostics, and agent are aimed at runtime services, not static-analysis tooling. The most useful parts (interfaces + CLI boundary) can be adopted without importing the library into the root package.

Recommendation: do not add a root-package dependency. Keep the existing FindingError and consider implementing go-error-family's consumer interfaces in a bridge subpackage, or adopt HandleError only in cmd/go-finding/main.go.

01 — Library Overview

What go-error-family is

go-error-family is a Go library that gives every error a behavioral Family: Rejection, Conflict, Transient, Corruption, or Infrastructure. From that Family, the library derives retry decisions, process exit codes, presentation tone, and audience targeting.

Family Retry? Exit Audience Designed for
Rejection No 1 User Bad input, unauthorized, not found
Conflict No 1 User Version mismatch, duplicate, state clash
Transient Yes 75 All Temporary infrastructure failure
Corruption No 65 Ops Damaged source of truth
Infrastructure No 69 Ops System cannot serve

The library is organized as a Go workspace:

  • root — core types, classification, constructors, CLI boundary
  • diagnose/ — concurrent diagnostic rules (filesystem, network)
  • diagnose/git — opt-in GitRule submodule
  • diagnose/postgres — opt-in PostgresRule submodule
  • agent/ — deterministic root-cause analysis + FixSteps
  • bridge/ — separate module integrating samber/oops

The central idea is sound: share the protocol (what an error means) without forcing consumers to share the implementation.

02 — PRO Arguments

What go-error-family does well

P1. Protocol-first, interface-driven design

The library exposes four tiny interfaces that any error type can implement. This lets consumers classify and handle errors without importing the library's concrete Error type. It is the Go idiom: accept interfaces, return structs. 

type Classified interface {
    error
    ErrorFamily() Family
}

P2. Zero dependencies in the root module

The core package depends only on the standard library. Submodules (git, postgres, bridge) carry their own dependencies, so consumers pay only for what they use. This aligns well with go-finding's minimal-dependency philosophy.

P3. Classification cascade is deliberate and well documented

The precedence chain is clear and deterministic:

  1. Multi-error (errors.Join) — first non-Transient wins
  2. Classified interface
  3. Retryable interface
  4. Registered sentinels
  5. Default Transient (fail-open)

The fail-open default is a deliberate product decision: unknown errors are retried rather than rejected, which is usually safer at boundaries.

P4. Honest, boundary-aware API

Several choices show architectural discipline:

  • The agent only analyzes; it does not execute shell commands. The consumer decides what to do with FixStep.Command.
  • HandleErrorWithContext is the canonical entry point; other handlers delegate to it.
  • A disabled agent returns an error instead of a synthetic result.
  • The sentinel registry is snapshotted before iteration, so errors.Is runs without holding a lock.

P5. Strong test coverage and quality gates

The project ships with table-driven tests, fuzz tests, benchmarks, and integration tests for diagnostic rules. Running the full suite (root + all submodules) passes cleanly: 

go test ./... -count=1 -timeout 120s   # ok all modules
golangci-lint run ./...                 # 0 issues

P6. Useful bridge to samber/oops

The bridge/ submodule lets a project use oops for rich observability (stack traces, source fragments, trace IDs) and still get go-error-family classification. This shows the library is designed to coexist, not conquer.

P7. CLI boundary handler is genuinely useful

HandleError turns a one-liner in main() into structured, user-facing output with What/Why/Fix/WayOut templates and a correct exit code. For command-line tools this removes boilerplate and improves UX.

03 — CONTRA Arguments

Where it falls short or introduces risk

C1. Go 1.26 requirement is aggressive

The library uses errors.AsType[T](), which is new in Go 1.26. At the time of review, Go 1.26 has only recently released. This sharply limits adoption and forces consumers to upgrade their toolchain. It also means the library cannot be used in projects that must support older Go versions.

C2. Young project with unproven ecosystem traction

v0.4.0 is pre-1.0. There is no broad production track record, few external consumers, and APIs may still change. The comparison with samber/oops notes oops has 41 releases and ~1k GitHub stars; go-error-family is niche by comparison.

C3. Context values are string-only

ErrorContext() map[string]string is simple and serializable, but it forces callers to stringify structured values. For richer observability (integers, nested objects, request bodies), consumers still need something like samber/oops or a custom type.

C4. No built-in stack traces or rich debugging context

Unlike samber/oops, the library does not capture stack traces, source fragments, or trace/span IDs. The diagnostic rules and agent help, but they are no replacement for a captured stack trace when debugging a production failure.

C5. Template substitution has an XSS footgun

The applyContext helper uses strings.ReplaceAll, not html/template. This is fine for stderr output but unsafe if the rendered message is ever embedded in HTML. The limitation is documented, but it means the library is not boundary-agnostic: consumers must escape values themselves for web output.

C6. Root package mixes protocol and presentation

HandleError, templates, and the CLI boundary live in the root package. The project's own earlier "top-5 stupidest things" doc flagged this as a structural issue (item #3) and proposed moving it to a cli subpackage. It was not moved, so the root package still couples protocol semantics with presentation concerns.

C7. Fail-open default can surprise

Unknown errors classify as Transient, which means IsRetryable(err) returns true for any unrecognized error. This is safe for many boundaries but can lead to infinite retry loops if a caller blindly retries every Transient error without inspecting the code or message.

C8. Many features are dead weight for library consumers

Diagnostics, Git/Postgres rules, agent analysis, and audience/tone metadata are designed for applications at runtime boundaries. A library like go-finding has no use for most of them; importing the root package still brings the conceptual weight even if the code is unused.

04 — Domain Fit for go-finding

How well does it map to static analysis?

go-finding's existing error system is built around static-analysis semantics: FindingError carries Category, Finding, File, and Position. go-error-family is built around runtime service semantics: retry, exit code, audience, tone.

go-finding concern go-error-family fit Verdict
Machine-readable error codes Coded interface / code string Good fit
Static-analysis categories 5 Families aimed at runtime behavior Poor fit
Finding / Position / File context Generic map[string]string only Lossy
CLI exit codes ExitCode(err) maps Family to sysexits Useful in cmd/
Retry semantics Only Transient is retryable Marginal
Root package dependency-free Importing root would add first non-stdlib dep Violation

The best mapping is interfaces, not replacement: FindingError can implement Coded, Classified, and Contextual without changing its shape, and cmd/go-finding/main.go can call errorfamily.HandleError at the boundary.

05 — Competitive Position

How it compares to alternatives

Library Strength Weakness vs. go-error-family
go-error-family Behavioral classification, exit codes, CLI boundary —

pkg/errors (archived) Stack traces, simple wrapping No classification or context model

go-error-family occupies a clear niche: it is lighter than oops/cockroachdb and more opinionated than stdlib. It is not a replacement for rich observability libraries, but it can complement them (as the bridge/ module demonstrates).

06 — Recommendations

What go-finding should do

Recommended: interface-level adoption only

Implement go-error-family's consumer interfaces on FindingError in a separate bridge subpackage (e.g., finding/errorfamily/) so the root package remains dependency-free. Adopt HandleError only in cmd/go-finding/main.go.

Effort: low. Risk: minimal. Breaking changes: none.

Not recommended: full replacement of FindingError

Replacing FindingError with errorfamily.Error would discard domain-specific fields (Finding, Position, File) and force static-analysis errors into runtime Families. The cost far exceeds the benefit.

Alternative: no adoption

go-finding's current error system is already idiomatic and domain-appropriate. Doing nothing is acceptable, though it leaves machine-readable codes and richer CLI output on the table.
