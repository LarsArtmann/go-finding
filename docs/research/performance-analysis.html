GPU Dependencies

go-finding is a CPU-bound, memory-efficient library with excellent single-thread performance for its core data operations and strong parallel scaling for detector execution. The primary performance concern is the FixEngine's edit application path, which exhibits super-linear memory scaling proportional to file content size × edit count. SARIF serialization is the second largest allocation source, though streaming mitigations already exist.

Strengths

Zero-allocation hot paths (Key, Equal early-return, FilterInPlace GC-safe). Parallel detector execution delivers ~5× throughput with 5 detectors. Streaming SARIF/JSON via json.Encoder avoids full-buffer allocation. Root package has zero external dependencies beyond stdlib.

Critical Bottleneck

FixEngine.applyEditsWithConflicts creates a new []byte per edit by appending three slices (result[:offset] + replacement + result[endOffset:]). This is O(file_size) per edit, yielding O(n × file_size) total — 443 MB allocated for 1000 edits. Fix: use bytes.Buffer or pre-allocated destination slice.

Critical

Moderate Concern

SARIF import/export generates 15–22 allocations per finding due to intermediate struct construction. Streaming variants (WriteSARIF, FindingsFromReader) already mitigate output-side allocation, but the per-finding struct graph remains allocation-heavy.

SHA-256 Cost Analysis

The hash-based ID path (GenerateID when pos.Line == 0) uses SHA-256 via crypto/sha256. This is 4× more expensive than the positional path (205 ns vs 50 ns) and allocates 8× more (208 B vs 72 B). The hash path includes:

  • sha256.New() — hash instance allocation
  • 3× writeLenField — binary encoding + Write calls
  • h.Sum() — digest allocation
  • hex.EncodeToString — hex string allocation
  • strings.Builder — final ID string assembly

For high-throughput pipelines with many position-less findings, consider caching IDs or switching to a faster hash (xxHash, FNV-1a) if collision resistance requirements allow.

GC Pressure Analysis

Zero-Allocation Hot Paths

Finding.Key() (3.4 ns, 0 allocs), Clone() simple (18 ns, 0 allocs), FilterInPlace (in-place compaction, 0 heap growth), Pipeline.DryRun (61 allocs for 10k findings — amortized to 0.006 allocs/finding). These paths are GC-neutral and safe for high-frequency invocation.

Moderate GC Pressure

Merge allocates ~700 KB per 1000 findings (Clone per finding). Correlate creates IntervalIndex + result Correlations per call. GroupByFile creates a map entry per unique file. All are proportional to input size with no hidden quadratic factors.

High GC Pressure

SARIF Import: 2233 allocs/100 findings = ~22 allocs per finding. Each findingFromSarResult creates Finding, Position, Range, RelatedRef slice, and Metadata map independently.

SARIF Export: 1510 allocs/100 findings = ~15 allocs per finding. findingToSARIF decomposes into sarifResult + locations + fixes + properties.

FixEngine: 20,036 allocs for 1000 edits — new []byte per edit.

Disk Space: Backup Directory

The FixApplier creates a temporary directory (os.MkdirTemp) at construction time. For each file modified, a backup copy is stored. Disk usage scales linearly with total file size modified: backup_size = Σ(file_sizes_modified). The backup directory is cleaned up via Close(), which calls os.RemoveAll. If the process crashes, backups persist in /tmp/go-finding-backups-*.

Subprocess Performance Characteristics

Output Capture

cmd.Output() captures the entire stdout into a single []byte buffer before parsing. For tools that produce very large JSON output (e.g., staticcheck on a monorepo with 10,000+ findings), this can consume significant memory. There is no streaming subprocess output — the full JSON is buffered, then parsed.

Parallel Subprocess Execution

When ParallelDetectors=true (default), all detectors run concurrently via errgroup.WithContext. This means multiple subprocess instances execute simultaneously, competing for CPU cores, memory, and disk I/O. The Go runtime's GOMAXPROCS does not limit subprocess parallelism — the OS scheduler determines actual concurrency.

Process Startup Overhead

Each exec.Command incurs: fork+exec syscall (~1-5 ms), dynamic linker loading, Go runtime initialization (for Go-based tools like staticcheck), and tool warmup (package loading, type checking). For govet on a medium project, this is typically 2–30 seconds — dwarfing all in-process computation.

Context Propagation

Context cancellation is propagated through all pipeline stages. The IsContextError() function is the canonical check used in retry, partial, and verify paths. context.Canceled and context.DeadlineExceeded are propagated immediately rather than silently swallowed. Per-detector timeouts (Config.DetectorTimeouts) override the global timeout.

ML Inference

go-finding has no GPU acceleration whatsoever. All computation runs on the CPU. This is the correct design decision for the current scope because:

Why GPU is Not Applicable

Static analysis is inherently branch-heavy, data-dependent computation. AST traversal, type inference, control-flow analysis, and rule matching involve irregular memory access patterns and conditional logic — the exact workload GPUs handle poorly. GPU SIMT architecture excels at uniform, lockstep computation (matrix math, image processing), not graph traversal.

Where GPU Could Help (Future)

1. Large-scale file scanning: Scanning millions of files for generated-file patterns (regex/substring) could benefit from GPU-parallel string matching. Currently handled by gogenfilter (CPU).

2. AI fix suggestions: FixStrategyAI is reserved but unimplemented. If LLM-based fix generation is added, GPU inference (via ONNX Runtime, CUDA) would be essential for local model execution.

3. Semantic similarity: Finding correlation could use embedding-based similarity (GPU-accelerated) instead of line-proximity heuristics.

Hardware Acceleration Present

The bytes.Index and bytes.Count functions used in SubstringProvider and LineShiftMap are SIMD-optimized by the Go runtime on supported platforms (AVX2/SSE4.2 on x86, NEON on ARM). This provides implicit hardware acceleration for string operations without explicit GPU code.

🎯Recommendations

Prioritized by impact (Pareto principle — 80% benefit from 20% of effort):

1. Fix FixEngine byte-copy bottleneck P0

Problem: applyEditsWithConflicts at fix_engine.go:169 creates a new []byte per edit via append(append(append(nil, result[:offset]...), replacement...), result[end:]...). This is O(F) per edit where F = file size.

Fix: Use bytes.Buffer with Write calls, or pre-allocate a destination slice and use copy(). Since edits are applied descending by offset, a single-pass bytes.Buffer from right to left eliminates all intermediate copies.

Expected impact: ~100× reduction in allocations for 1000 edits (443 MB → ~5 MB). Wall time: 291s → ~3s.

Critical ~2 hours

2. Add file content cache for FixApplier P1

Problem: Same file read up to 4× per iteration (GeneratedFileFilter, ByteLevelConflictDetection, Backup, Apply).

Fix: Add a map[string][]byte content cache to FixApplier (or a FileContentCache interface). Populate on first read, invalidate after write.

Expected impact: 4× reduction in file I/O for fix-heavy workloads. Especially impactful for monorepos with large files on slow disks.

High ~4 hours

3. Pool SARIF struct allocations P1

Problem: SARIF export creates 15 allocs/finding, import creates 22. These are short-lived structs immediately serialized/deserialized.

Fix: Use sync.Pool for sarifResult, sarifLocation, sarifRegion structs. Reset fields on return.

Expected impact: ~50% reduction in GC pressure during SARIF batch processing. Throughput improvement for large result sets (10k+ findings).

Moderate ~6 hours

4. Stream subprocess output P2

Problem: cmd.Output() buffers entire subprocess stdout before parsing. For staticcheck on a large repo, this can be 100+ MB of JSON.

Fix: Use cmd.StdoutPipe() + json.Decoder to stream-parse JSON output line by line or token by token.

Expected impact: Peak memory reduction proportional to output size. Enables processing of very large tool outputs without OOM.

Moderate ~8 hours

5. Cache LineOffsetIndex across findings P2

Problem: LineProvider.Edits calls buildLineOffsetIndex(content) for each finding, even when multiple findings target the same file.

Fix: Accept an optional pre-built index, or have FixEngine build the index once per file and pass it to all providers for that file.

Expected impact: Eliminates redundant O(F) line scans when applying multiple fixes to the same file.

Low-Med ~3 hours

6. Pre-allocate result slices P3

Problem: Several functions use var result []T (nil slice) then append, causing 2-3 reallocations for large inputs.

Fix: Use make([]T, 0, len(input)) where the result size is bounded by input size. Already done in Filter and Combine — extend to correlateByOverlap, DetectConflicts, DifferentFindings.

Expected impact: Minor (~5-10% allocation reduction) but free.

Low ~2 hours

Additional Performance Characteristics

Startup Cost

Near-zero. No init() functions in hot paths. The category_linter.go map (70+ entries) is a package-level var initialized at first use. DetectrackRegistry constructors are lazy.

Error Handling Overhead

Success paths have zero error-handling overhead. Error paths use fmt.Errorf with %w (one allocation for the formatted string) and errors.Join (one allocation for the joined error slice). Validation uses errors.Join(errs...) which returns nil for empty slices — no allocation when valid.

Retry & Backoff

RetryDetector uses exponential backoff with jitter: delay = min(2^attempt × baseDelay, maxDelay) + rand(quarter). Uses math/rand/v2 (lock-free, no global mutex contention). Backoff is clamped to MaxDelay after jitter to prevent cap overshoot.

CPU Profiling Support

The CLI supports -cpuprof and -memprof flags for runtime/pprof. Profiles can be analyzed with go tool pprof. The benchmark suite in bench_test.go covers 15 operations with b.ReportAllocs() on allocation-sensitive paths.

Binary Size

The root package compiles to a lean binary with only stdlib dependencies. The full CLI with all subpackages (pipeline, analysis, gogenfilter, yaml) adds approximately 8-12 MB to the binary. GoReleaser config supports UPX compression and SBOM generation.
