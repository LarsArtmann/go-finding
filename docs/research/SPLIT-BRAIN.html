🔑 What is a split-brain?

A split-brain is not just "two ways to do the same thing" (that's normal API surface). It's when the two ways disagree about the truth. The signature of a split-brain:

  • You ask the same question in two places and get different answers.
  • Two fields hold overlapping information with no invariant linking them.
  • A round-trip (export → import) silently changes the data.
  • A constructor produces a value that the validator rejects.

Issue 1 — Position Zero-Value Lies About Its Own State

#1 The most fundamental type in the library returns contradictory answers Critical ✅ Resolved Verified

“What's the split-brain?”

Position is the most-used type in the library — every Finding has one, every Range has two, every RelatedRef has one. Its zero value Position{} lies about itself: IsZero() and HasOffset() both return true for the same value, but they mean opposite things.

position.go:21 — the field comment
Offset int `json:"offset,omitempty"`
// 0-based byte offset; -1 = not set
range.go:170 — the accessor
func (p Position) HasOffset() bool {
    return p.Offset >= 0  // 0 means "byte 0"
}

But the zero value of int is 0, not -1. So Position{} has Offset == 0, which:

  • IsZero() reports as “unset” (position.go:30-32)
  • HasOffset() reports as “byte offset 0 is set” (range.go:170-172)
  • Range.Length() treats 0 as set via if r.Start.Offset < 0 (range.go:66)
  • Range.HasEnd() treats 0 as set via r.End.Offset >= 0 (range.go:35)
  • Range.containsByOffset() treats 0 as set via p.Offset >= 0 (range.go:137)

🧪 Reproduction (verified)

/tmp/verify_splitbrain.go (excerpt)
p := finding.Position{}
fmt.Println(p.IsZero())     // → true   "I have no information"
fmt.Println(p.HasOffset())  // → true   "I have an offset of 0"
fmt.Println(p.Offset)       // → 0

The type asserts two contradictory facts about the same byte.

💥 Why it matters

Every consumer that touches Position.Offset must know which interpretation to use. A junior developer writing if pos.HasOffset() { seek(pos.Offset) } will silently seek to byte 0 when they meant “position wasn't set.” The bug only surfaces when a finding legitimately has no offset — exactly the case where seeking to byte 0 corrupts data. Tests rarely catch this because most test fixtures set offsets explicitly.

🔧 How to fix — three options
A Adopt -1 sentinel for “unset” offset (recommended). Change NewFinding, Pos(), NewRange, and every offset-setting call site to use -1 as default. Position{} would then have Offset == 0 (meaning byte 0) — make the zero value invalid by introducing Position.IsValid() checks at boundaries.
Pro: least invasive; HasOffset() already implements this check.
Con: negative offset is a footgun if not validated; can't use uint.
B Switch Offset to *int. nil unambiguously means “unset.”
Pro: impossible to confuse; idiomatic Go.
Con: breaking API change; nil-deref risk at every call site; JSON encoding changes.
C Add explicit HasOffset bool field.
Pro: explicit; no sentinel confusion.
Con: struct grows; two fields must be kept in sync — a new split-brain.

Recommended path: Option A. Update Position{} construction in NewFinding, Pos(), NewRange, and FromLSP() to set Offset: -1. Add a go test -race test that constructs Position{} and asserts !HasOffset() && IsZero().

🧪 Tests to add

  • TestPositionZeroValue_ConsistentSelfReports — assert Position{}.IsZero() ⟺ !Position{}.HasOffset().
  • TestRange_Length_ZeroOffsetIsUnset — Range{Start: Position{}}.Length() returns 0.
  • Fuzz: random Position values, assert HasOffset() never lies.

📍 Files to touch

position.go:11-32 range.go:35, 66, 137, 170-172 finding.go:52-68 (NewFinding) lsp.go:139-170 (FromLSP) sarif_import.go:141-177 (applySarifPosition)

Issue 2 — Two Valid “No Fix” States: "" vs "none"

#2 FixStrategy has two ways to say “no fix,” and they aren't even Equal() Critical ✅ Resolved Verified

What's the split-brain?

FixStrategy is a string enum with four declared constants. But the empty string "" — the zero value — is also a valid “no fix” state, distinct from the explicit FixStrategyNone = "none".

fix_strategy.go:8 — explicit constant
FixStrategyNone FixStrategy = "none"
finding_validate.go:41 — implicit acceptance 
if f.FixStrategy != "" && !f.FixStrategy.IsValid() {
    // error
}
// "" silently accepted as valid

FixStrategy.IsValid() returns false for "" (it only matches the 4 constants). But Finding.Validate() explicitly skips the check when FixStrategy == "". So the validator disagrees with the type's own validity method.

🧪 Reproduction (verified)

f2 := Finding{FixStrategy: ""}    // empty
f3 := Finding{FixStrategy: "none"} // explicit

f2.Validate()   // → nil   (accepted)
f3.Validate()   // → nil   (accepted)
f2.Equal(f3)    // → false  (different bytes!)
f2.FixStrategy.IsValid()  // → false
f3.FixStrategy.IsValid()  // → true

Two findings that are both “no fix” fail Equal(). Diff, dedup, and merge all see them as different. Worse: Equal() compares f.FixStrategy != other.FixStrategy directly (finding_equal.go:43), so a default-constructed Finding{} and an NewFinding(...) result (which sets "none") compare unequal on strategy even when everything else matches.

💥 Why it matters

  • Diff lies: Diff() reports two equivalent findings as “modified” because their strategies differ as strings.
  • SARIF round-trip: empty strategy is exported as "" in the property bag; on import, FixStrategy("").IsValid() fails, so the field is left empty — works, but for the wrong reason.
  • Constructor asymmetry: NewFinding() normalizes to "none" (finding.go:65), but struct-literal construction Finding{...} leaves "". Two findings built two valid ways differ.
🔧 How to fix — pick one canonical form
A Normalize "" → "none" in Validate() (recommended, minimal blast radius). Change finding_validate.go:41 to: 
if f.FixStrategy == "" {
    f.FixStrategy = FixStrategyNone  // normalize
} else if !f.FixStrategy.IsValid() {
    errs = append(errs, NewValidationError(...))
}
Or do it in Builder.Build() and add a normalizing helper NormalizeFixStrategy(FixStrategy) FixStrategy that other entry points call.
B Make "" invalid. Reject it in Validate(). Update every constructor to set "none" explicitly. This is a breaking change for any consumer that relies on the zero value.
C Make "none" the zero value. Replace FixStrategy string with a type whose zero value is "none" — impossible without changing the underlying type. Not viable.

Recommended: Option A. Add a single normalization point and route every public entry point (NewFinding, FromLSP, findingFromSarResult, Builder.Build, Validate) through it.

🧪 Tests to add

  • TestFixStrategy_EmptyEqualsNone — after normalization, Finding{Strategy:""}.Equal(Finding{Strategy:"none"}) is true.
  • TestFinding_Validate_NormalizesEmptyStrategy — verify the field is mutated to "none".
  • Property test: for any FixStrategy, after Validate(), IsValid() returns true.

📍 Files to touch

finding_validate.go:41-45 fix_strategy.go:6-18 (add normalization helper) finding.go:65 (NewFinding — already correct, keep as canonical example) lsp.go:158 (FromLSP — sets FixStrategyNone, OK) sarif_import.go:74-97 (default for unset strategy)

Issue 3 — Four “Is This Fixable?” Predicates Disagree

#3 HasFix, IsAutoFixable, HasCodeChange, HasSuggestion answer the same question four ways High ✅ Resolved Verified

What's the split-brain?

Finding has four predicates about fixability, each answering a slightly different question with overlapping semantics. For a single Finding, they routinely return different combinations of true/false — and one combination is internally contradictory.

Method Asks… Defined at
HasFix() “Is there any fix at all?” finding_methods.go:65
IsAutoFixable() “Can the pipeline apply it without human help?” finding_methods.go:82
HasCodeChange() “Are BeforeCode or AfterCode non-empty?” (low-level) finding_methods.go:126
HasSuggestion() “Is there suggestion text?” finding_methods.go:87

🧪 Reproduction — four findings, four contradictory verdicts (verified) 

// Case A: FixStrategyDirect with no code (invalid per Validate!)
f := Finding{FixStrategy: FixStrategyDirect}
f.HasFix()         // → true   ← lies
f.IsAutoFixable()  // → false
f.HasCodeChange()  // → false
f.Validate()       // → ERROR: "FixStrategyDirect requires BeforeCode or AfterCode"

// Case B: Suggest + AfterCode
f := Finding{FixStrategy: FixStrategySuggest, AfterCode: "fixed()"}
f.HasFix()         // → true
f.IsAutoFixable()  // → false
f.HasCodeChange()  // → true
f.HasSuggestion()  // → false   ← surprising

Case A is the worst: HasFix() returns true for a finding that Validate() rejects. The type claims to be fixable while simultaneously being invalid.

💥 Why it matters

Pipeline.DefaultTriageFunc (pipeline_detect.go:159-177) calls IsAutoFixable() then HasFix(): 

if f.IsAutoFixable() {
    result.Direct = append(result.Direct, f)
} else if f.HasFix() {
    result.Suggest = append(result.Suggest, f)
} else {
    result.None = append(result.None, f)
}

So a FixStrategyDirect-without-code finding is silently routed to Suggest, contradicting its own declared strategy. The pipeline papers over the contradiction, but the Suggest bucket now contains a finding whose FixStrategy says “direct.” Any consumer reading result.Suggest[i].FixStrategy will see "direct" — a lie.

🔧 How to fix
  1. Make HasFix() respect Validate(). Change finding_methods.go:65-76: 
    func (f Finding) HasFix() bool {
    switch f.FixStrategy {
    case FixStrategyNone, "":  // ← also normalize empty
        return false
    case FixStrategyDirect:
        return f.BeforeCode != "" || f.AfterCode != ""  // ← require code
    case FixStrategySuggest, FixStrategyAI:
        return f.AfterCode != ""
    default:
        return false
    }
}
    Now HasFix() is the strict superset of IsAutoFixable(): if HasFix() is true, the finding is at least valid as a fix.
  2. Document the lattice in finding_methods.go: 
    // HasFix ⊇ IsAutoFixable. HasCodeChange is the low-level signal.
// HasSuggestion is orthogonal (may be true even when HasFix is false).
  3. Replace the HasFix()-then-IsAutoFixable() cascade in DefaultTriageFunc with a single decision: 
    switch {
case f.IsAutoFixable():
    result.Direct = append(...)
case f.HasFix():
    result.Suggest = append(...)
default:
    result.None = append(...)
}
    (already structurally correct, but only safe after fix #1).

🧪 Tests to add

  • TestHasFix_NeverTrueForInvalidFindings — every finding where HasFix() returns true must also pass Validate().
  • TestTriage_DirectWithoutCode_GoesToNone — invalid Direct findings are not silently demoted to Suggest.
  • Property test: IsAutoFixable() ⟹ HasFix().

📍 Files to touch

finding_methods.go:65-76 (HasFix) pipeline/pipeline_detect.go:159-177 (DefaultTriageFunc) sarif_export.go:198-218 (sarifFixes — depends on HasFix)

Issue 4 — Category and Tags Share Vocabulary, Can Conflict

#4 A Finding has two classification fields with overlapping constant sets and no invariant linking them High ✅ Resolved Verified

What's the split-brain?

Finding.Category is a single-value classification. Finding.Tags is a multi-value classification. Both use lowercase-hyphenated strings, and six values are defined as constants in both types:

category.go:13-30
CategorySecurity      = "security"
CategoryStyle         = "style"
CategoryPerformance   = "performance"
CategoryCorrectness   = "correctness"
CategoryComplexity    = "complexity"
CategoryDocumentation = "documentation"
// + 10 more
tag.go:7-18
TagSecurity      = "security"
TagStyle         = "style"
TagPerformance   = "performance"
TagCorrectness   = "correctness"
TagComplexity    = "complexity"
TagDocumentation = "documentation"
// + 4 more

The following is legal and silently constructed:

f := Finding{
    Category: CategorySecurity,
    Tags:     []Tag{TagPerformance, TagSecurity},  // ← contradicts Category
}

Is this finding about security or performance? The data model has no opinion. Nothing in Validate() checks for consistency. The consumer must guess.

💥 Why it matters

  • Filter ambiguity. ByCategory(CategorySecurity) and ByCategory via Tags give different result sets for the same logical query. There's no FilterByClassification that checks both.
  • SARIF doubles the data. sarifProperties() emits both go-finding/category and go-finding/tags — same string in two property-bag keys.
  • Summary counts are ambiguous. Summary.ByCategory counts by single category; Summary has no ByTag. A multi-tagged finding is undercounted.
🔧 How to fix — two strategic options
A Deprecate Category in favor of Tags only (recommended long-term). Tags is strictly more expressive. Category becomes “the first/primary tag,” derivable. Mark Category deprecated in v0.8.0, remove in v1.0.0 alongside other deprecated APIs.
Pro: eliminates the entire class of bug; simplifies Summary.
Con: breaking change; requires migration guide.
B Add a validation invariant (minimal fix). In Validate(), reject findings where Category appears in Tags with a conflicting value (e.g. Category="security", Tags=["performance"] alone). Allow Tags to contain the category.
Pro: non-breaking; surfaces the conflict at construction.
Con: doesn't remove the redundancy, just forbids the worst case.

Recommended path for v1.0.0: Option B now (stops the bleeding), Option A in v1.0.0 alongside the other breaking changes. Document the decision in docs/architecture-decisions.md as ADR #12.

🧪 Tests to add

  • TestValidate_CategoryTagConsistency — conflicting Category/Tags fails validation.
  • TestTags_SubsumeCategory — if Category="security", the finding is queryable as security via Tags too.
  • After A: TestCategory_DeprecatedEquivalence — Category accessor returns Tags[0] or derived primary.

📍 Files to touch

category.go:13-30 tag.go:7-18 finding_validate.go:59-65 (add invariant) sarif_export.go:258-272 (sarifProperties) report.go:69-78 (Summary.ByCategory vs missing ByTag)

Issue 5 — Three Duration Fields, None Authoritative

#5 Summary.DurationMs, Metrics.TotalDuration(), MetricsSnapshot.TotalDuration — pick one High ✅ Resolved Verified

What's the split-brain?

“How long did this take?” has three answers in three places:

Field Type Where Set by Used by
Summary.DurationMs int64 (milliseconds) report.go:76 Caller, manually Nothing in the codebase (vestigial)
Metrics.TotalDuration() time.Duration pipeline/metrics.go:98 Pipeline (start/end timestamps) cmd/go-finding/main.go:222
MetricsSnapshot.TotalDuration time.Duration pipeline/metrics.go:131 Computed in Snapshot() Pipeline tests, CLI

The field comment on Summary.DurationMs even admits the problem: 

DurationMs int64 `json:"durationMs,omitempty"`
// Execution time (caller-set; not computed by ComputeSummary)

ComputeSummary() (report.go:179-250) computes Total, BySeverity, ByCategory, ByFixStrategy, FilesAffected, Suppressed — but pointedly not DurationMs. A consumer who builds a Report directly (without the pipeline) gets DurationMs == 0 forever, unless they remember to set it. A consumer who runs the pipeline gets an accurate duration in Metrics, but Summary.DurationMs is still 0.

💥 Why it matters

  • JSON consumers get contradictory data. A SARIF/JSON report shows "durationMs": 0 in the summary while the pipeline metrics show real time.
  • No single source of truth. Consumers reading docs see both fields and don't know which to trust.
  • AGENTS.md documents this as a known gotcha — meaning even the maintainer acknowledges the confusion but hasn't resolved it.
🔧 How to fix — two options
A Remove Summary.DurationMs; point consumers to Metrics (recommended). The pipeline already produces authoritative timing. Report without a pipeline has no meaningful duration by definition.
Pro: one source of truth; matches reality.
Con: breaking change for any consumer reading Summary.DurationMs.
B Make ComputeSummary() accept optional metrics and populate DurationMs. Add ComputeSummaryFromMetrics(m *Metrics) that sets DurationMs from m.TotalDuration().
Pro: non-breaking; both fields stay populated and consistent.
Con: two fields still exist; need to keep them in sync going forward.

Recommended: Option A for v1.0.0 (clean break with other breaking changes). Option B as a v0.8.0 compatibility shim if needed.

🧪 Tests to add

  • TestReport_NoDurationField_AfterRemoval — verify the JSON no longer contains durationMs.
  • Or: TestComputeSummary_PopulatesDurationFromMetrics — if Option B.
  • Update report_extra_test.go:77-92 (current TestComputeSummary_PreservesDurationMs — delete or repurpose).

📍 Files to touch

report.go:76 report.go:179-250 (ComputeSummary) report_extra_test.go:77-92 AGENTS.md (remove the gotcha entry)

Issue 6 — Three Different “Finding Identity” Definitions

#6 Key(), dedupKey(), and GenerateID() use different fields to answer “are these the same finding?” Medium ✅ Resolved Verified

What's the split-brain?

“Are these two findings the same?” has three different answers depending on which function you ask:

Function Identity includes Identity excludes File
Finding.Key() ID, or ToolName + File + Rule + Message Line, Column finding_validate.go:114
dedupKey() (ByID) ID everything else merge.go:139
dedupKey() (ByPosition) ToolName + File + Line + Column Rule, Message merge.go:145
dedupKey() (ByRule) Rule + File + Line + Column ToolName, Message merge.go:161
GenerateID() ToolName + Rule + File + Line (+ Column) Message id.go:23

So if two detectors both report “nil deref at main.go:10:5,” they have the same GenerateID, same dedupKey(ByPosition) (if same tool) or different (if different tools!), but their Key() differs if their messages differ. Three functions, three opinions on identity.

💥 Why it matters

  • Key() is used by external consumers for dedup; dedupKey() is used by Combine(). If they disagree, two reports deduped externally may not dedup internally, or vice versa.
  • The separator differs: Key() uses "\x00" (NUL), dedupKey() uses ":". Different collision properties.
  • Key() includes Message, so rewording a message creates a “new” finding.
🔧 How to fix
  1. Document the canonical identity in a single place: “Two findings are identical iff their GenerateID outputs are equal.”
  2. Make Key() consistent with GenerateID — drop Message, add Line/Column. Or deprecate Key() in favor of GenerateID.
  3. Document each DeduplicateBy strategy as a deliberate relaxation of canonical identity, not a competing definition.

🧪 Tests to add

  • TestKey_EqualsGenerateID_WhenIDSet — verify the two agree.
  • Property test: for any two findings, if GenerateID equal then Key() equal.

📍 Files to touch

finding_validate.go:114-120 (Key) merge.go:137-180 (dedupKey) id.go:23-73 (GenerateID) docs/DOMAIN_LANGUAGE.md (add Identity definition)

Issue 7 — SARIF Exports Two Disagreeing Regions Per Finding

#7 Location region uses Range.End; fix region ignores it and emits a zero-length span Medium ✅ Resolved Verified

What's the split-brain?

In sarif_export.go, two functions in the same file compute a SARIF region from a Finding using different rules:

sarif_export.go:171 — findingRegion (location) 
region.StartLine = f.Position.Line
region.StartColumn = f.Position.Column
if f.Range != nil && f.Range.HasEnd() {
    region.EndLine = f.Range.End.Line
    region.EndColumn = f.Range.End.Column
}
sarif_export.go:189 — findingFixRegion (fix) 
return sarifRegion{
    StartLine:   f.Position.Line,
    StartColumn: f.Position.Column,
    EndLine:     f.Position.Line,   // ← ignores Range!
    EndColumn:   f.Position.Column, // ← ignores Range!
}

🧪 Reproduction (verified)

A finding with Range from line 10 col 5 to line 20 col 10 produces this SARIF (excerpt): 

"locations": [{
    "region": {
        "startLine": 10, "startColumn": 5,
        "endLine": 20, "endColumn": 10      ← correct
    }
}],
"fixes": [{
    "artifactChanges": [{
        "replacements": [{
            "deletedRegion": {
                "startLine": 10, "startColumn": 5,
                "endLine": 10, "endColumn": 5     ← LIE: zero bytes
            },
            "insertedText": { "text": "new" }
        }]
    }]
}]

The fix claims to delete zero bytes at one position and insert "new". A SARIF consumer applying this fix literally inserts text at column 5 without deleting anything — completely wrong for a finding that actually spans 10 lines.

💥 Why it matters

  • SARIF consumers (GitHub Code Scanning, VSCode, Azure DevOps) that apply fixes get wrong results.
  • The exported SARIF contradicts itself: the location says the issue spans lines 10-20, the fix says it touches only line 10.
  • Round-trip is partially lossy: re-importing recovers the Range from the location, but the fix region's lie is preserved.
🔧 How to fix

Make findingFixRegion use the same logic as findingRegion. Either extract a shared helper or have findingFixRegion call findingRegion: 

func findingFixRegion(f Finding) sarifRegion {
    region := findingRegion(f)  // ← shared logic
    if region.EndLine == 0 {
        region.EndLine = f.Position.Line
        region.EndColumn = f.Position.Column
    }
    return region
}

This is a 5-line fix. The hard part is deciding what to do when Range is nil — the current zero-length behavior is correct in that case (no span to delete).

🧪 Tests to add

  • TestSARIF_FixRegionMatchesLocationRegion_WhenRangeSet — for a multi-line finding, exported deletedRegion equals location region.
  • Round-trip test: multi-line finding with Direct fix → SARIF → re-import → Range preserved.
  • Update sarif_roundtrip_test.go with a multi-line fixture.

📍 Files to touch

sarif_export.go:189-196 (findingFixRegion) sarif_export.go:171-187 (findingRegion — reference) sarif_roundtrip_test.go

Issue 8 — SARIF Property Bag Uses map[string]any Against Project Doctrine

#8 Finding.Metadata is map[string]string by design; sarifResult.Properties is map[string]any Medium ✅ Resolved Verified

What's the split-brain?

finding.go:36-47 — the doctrine
// We intentionally have only Metadata
// (map[string]string), NOT a Properties
// map[string]any.
sarif_types.go:65 — the violation
type sarifResult struct {
    ...
    Properties map[string]any
        `json:"properties,omitempty"`
}

The project has an explicit, documented design decision: string-to-string only, for lossless interchange. But the SARIF layer — which is the primary interchange format — uses map[string]any internally. The conversion happens in sarifProperties() (sarif_export.go:258) and applySarifProperties() (sarif_import.go:180), which silently coerce types (e.g. Tags []Tag → []any; on import, type-assert back).

💥 Why it matters

  • Type-assertion boilerplate on every import — see the 5+ switch v := props[k].(type) blocks.
  • Silent loss: if a Tag value isn't a string on import, it's dropped with no error.
  • Doctrine erosion: a contributor reading the doctrine in finding.go won't know the SARIF layer violates it.
Important nuance: SARIF 2.1.0 itself specifies propertyBag.properties as map[string,any — so the SARIF wire format requires this. The split-brain is between the public Go API (string-only) and the internal SARIF layer (any). The fix is not to change the wire format, but to document the boundary and centralize the coercion.
🔧 How to fix
  1. Add a doctrine note in sarif_types.go: 
    // sarifResult.Properties is map[string]any because SARIF 2.1.0
// requires it. The Finding.Metadata doctrine (string-only) is preserved
// at the public API boundary; see sarifProperties/applySarifProperties
// for the coercion layer.
  2. Centralize coercion in applySarifProperties: make every property read go through a single stringProp-style helper that returns (string, ok) and logs losses.
  3. Test for losslessness: property test — for any map[string]string, after export→import, all keys are recovered.

🧪 Tests to add

  • TestSarifProperties_RoundTripPreservesAllMetadata — every metadata entry survives.
  • TestSarifProperties_RejectsNonStringOnImport — non-string values are dropped with a debug log, not silently.

📍 Files to touch

sarif_types.go:57-66 (document) sarif_export.go:258-299 sarif_import.go:180-264

Issue 9 — Suppression Validation Accepts Unknown Kinds

#9 Suppression.IsValid() accepts any non-empty Kind; SuppressionKind.IsValid() rejects most Low ✅ Resolved Verified

What's the split-brain?

suppression.go:33 — structural check
func (s *Suppression) IsValid() bool {
    return s.Kind != "" && s.Rule != ""
}
suppression.go:48 — semantic check
func (k SuppressionKind) IsValid() bool {
    switch k {
    case InSource, InConfig, InReview:
        return true
    }
    return false
}

Suppression{Kind: "garbage", Rule: "x"}.IsValid() returns true. SuppressionKind("garbage").IsValid() returns false. Finding.Validate() calls the weaker one (finding_validate.go:85-89).

💥 Why it matters

A typo like Kind: "in-soruce" passes validation and silently produces a suppression that no consumer recognizes. The data enters the system, gets serialized to SARIF, and propagates. Low-severity because suppressions are rare, but the pattern is the same as Issue 2 — two validation methods disagreeing.

🔧 How to fix (1-line change)
// suppression.go:33
func (s *Suppression) IsValid() bool {
    return s != nil && s.Kind.IsValid() && s.Rule != ""
}

  • TestSuppression_RejectsUnknownKind — Suppression{Kind: "garbage", Rule: "x"}.IsValid() is false.
  • TestValidate_FindingWithBadSuppressionKind — Validate() returns an error.

Issue 10 — Category and Tag Have Twin IsValid / IsStandard Methods

#10 Two validity methods per type, no documented rule for which to call when Low ✅ Resolved Verified

What's the split-brain?

Issue 11 — Free-Function / Method Name Shadowing

#11 HasFix and HasSuggestion exist as both Finding methods and package-level functions Cosmetic ✅ Resolved Verified

What's the split-brain?

finding_methods.go:65 — method
func (f Finding) HasFix() bool {
    ...
}
filter.go:153 — free function
func HasFix(f Finding) bool {
    return f.HasFix()
}

Same pattern for HasSuggestion (finding_methods.go:87 / filter.go:158).

Go disambiguates these (f.HasFix() vs finding.HasFix(f)), so it's not a correctness bug. But it's a naming smell that violates the project's own “names are contracts” principle: a reader seeing HasFix in an IDE autocomplete gets two entries and must guess which is canonical.

🔧 How to fix

Rename the free functions in filter.go to fit the ByX / WithX convention used by their neighbors: 

// Old (filter.go:153, 158):
func HasFix(f Finding) bool
func HasSuggestion(f Finding) bool

// New (used as FilterFunc values, like BySeverity etc.):
func WithFix(f Finding) bool         // or: FilterHasFix
func WithSuggestion(f Finding) bool  // or: FilterHasSuggestion

Migration: the free functions are exported. Deprecate them with a comment for one release, then remove in v1.0.0.

🔀 Cross-Cutting Patterns

Three themes recur across the 11 issues. Fixing the pattern prevents the next bug.

Pattern 1 — “Two validators, one truth”

Issues #2, #9, #10 all follow the same shape: a type has a validity method, and a containing type has its own validity method that uses a weaker check. The two methods disagree about what's valid.

Fix the pattern: adopt a project rule — “a type's Validate() must transitively call Validate()/IsValid() on every nested typed field.” Add a lint rule or test that enforces it.

Pattern 2 — “Constructor skips normalization”

Issues #1 and #2 both allow struct-literal construction to bypass normalization that constructors apply. Finding{} has FixStrategy: "" and Position{} has Offset: 0; NewFinding() normalizes the former but not the latter.

Fix the pattern: make Validate() normalizing where possible (mutate fields to canonical form), so even struct-literal construction self-corrects at the next validation boundary. Where mutation is unsafe (concurrency), document the canonical constructor as the only supported path and have tests assert that.

Pattern 3 — “Same concept, two fields”

Issues #4 (Category/Tags), #5 (three durations), #6 (three identity keys), #7 (two SARIF regions) all store the same fact in multiple places with no invariant linking them.

Fix the pattern: when adding a field that overlaps an existing one, add a // INVARIANT: comment and a validation check. Better: derive one from the other (func (f Finding) DurationMs() int64 instead of a stored field).
