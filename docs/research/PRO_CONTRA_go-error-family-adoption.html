Should go-finding adopt go-error-family?

Research report — 2026-06-01 — Analysis of integrating github.com/larsartmann/go-error-family into github.com/larsartmann/go-finding

Executive Summary

Verdict: Partial adoption recommended

Do NOT replace FindingError with errorfamily.Error. The two systems serve different domains and both are well-designed for their purpose. Instead, implement go-error-family's interfaces on FindingError for interoperability, and adopt HandleError in the CLI layer for richer output.

Key reason: go-finding's errors carry static-analysis domain context (Finding, File, Position) that go-error-family was never designed for. The Families map poorly to static analysis semantics. But the interfaces and CLI boundary logic are universally useful.

2. What go-error-family Offers

The Five Families

Family Retry? Exit Fault Tone Designed for
Rejection No 1 User Instructional Bad input, unauthorized
Conflict No 1 User Explanatory Version mismatch, duplicate
Transient Yes 75 System Reassuring Temporary infra failure
Corruption No 65 System Urgent Damaged source of truth
Infrastructure No 69 System Apologetic System cannot serve

Key Capabilities

  • Classification system — 5-level precedence chain: multi-error → Classified → Retryable → registered sentinels → default Transient
  • CLI boundary — HandleError(): classify → format with templates → stderr → exit code
  • Message templates — Wix-style What/Why/Fix/WayOut with {{.key}} substitution
  • Diagnostics — Concurrent rules (Filesystem, Network, Git, Postgres) for root-cause analysis
  • Agent analysis — Debug agent for AI-assisted error explanation
  • Consumer interfaces — Coded, Classified, Contextual, Retryable — composable, third-party friendly

4. PRO Arguments

P1. Machine-readable error codes

go-finding errors currently carry a category ("io") but no specific code. Two different IO errors are indistinguishable programmatically. errorfamily.Coded adds ErrorCode() string enabling "file.backup.read" vs "sarif.parse.invalid".

P2. Retry semantics baked into error types

Pipeline's retry.go retries all detector errors uniformly. With Classified/Retryable, detectors could signal which errors are worth retrying. Transient = retry with backoff; everything else = fail immediately. This is more precise than the current blanket approach.

P3. Richer CLI boundary output

HandleError() provides structured What/Why/Fix/WayOut output with template overrides. Currently the CLI just prints fmt.Errorf chains. Adopting HandleError in cmd/go-finding/main.go would give users actionable fix suggestions instead of raw error chains.

P4. Zero external dependencies

go-error-family is stdlib-only. No transitive dependency explosion. Compatible with go-finding's minimal dependency philosophy.

P5. Composable interfaces enable third-party integration

If go-finding's FindingError implements Coded, Classified, Contextual, then any consumer already using go-error-family can classify and handle go-finding errors without import coupling. This is the "share protocols, not implementations" pattern.

P6. Contextual error details via map[string]string

WithContext("host", "localhost") pattern matches go-finding's existing Metadata map[string]string convention. FindingError could gain context without breaking anything, and diagnostic rules could key off it.

P7. Diagnostic rules for common failure modes

go-finding's pipeline frequently hits filesystem errors (file_backup.go, fix_applier.go). The FilesystemRule from go-error-family could automatically diagnose "permission denied" / "disk full" / "path not found" with structured findings.

5. CONTRA Arguments

C1. Domain mismatch — Families designed for CLI/HTTP, not static analysis

The five Families encode a retry/audience/tone model for user-facing systems. Static analysis has different concerns:

  • Corruption = "source of truth damaged" — when does a static analysis tool encounter this?
  • Infrastructure = "system cannot serve" — only the CLI entry point applies; the library never "serves"
  • Transient = "retry with backoff" — pipeline has its own retry logic independent of error classification

Forcing go-finding's errors into these Families adds semantic friction without proportional gain.

C2. FindingError carries domain-specific fields with no equivalent

FindingError has Finding *Finding, File string, Position *Position. These are core to go-finding's domain and have no parallel in go-error-family. Replacing FindingError means either:

  • Losing this context (unacceptable), or
  • Embedding errorfamily.Error inside a new wrapper (reinventing FindingError with extra steps)

C3. Violates design principle #12: Root package dependency-free

AGENTS.md states: "golang.org/x/tools only in analysis/ subpackage". Importing errorfamily in the root package (where errors.go lives) would add the first non-stdlib dependency to the root. This is a deliberate architectural boundary.

C4. Massive migration surface — 66 fmt.Errorf, 22 sentinels, ~50 test files

Full adoption would touch:

  • 66 fmt.Errorf calls across all packages
  • 22 sentinel error definitions
  • 8 errors.Join aggregation points
  • ~49 test files checking error types
  • All exported API (ErrValidation, NewValidationError, etc.) — breaking change

Risk: every touched file is a regression opportunity. The current system works.

C5. errors.Is semantics conflict

FindingError.Is() matches any error with the same category to the corresponding sentinel. errorfamily.Error.Is() matches code + family. These are fundamentally different:

  • go-finding: errors.Is(anyIOError, ErrIO) → true (category match)
  • go-error-family: errors.Is(err1, err2) → only if same code AND family

Merging would break one or both matching strategies.

C6. Pipeline retry logic is already independent

pipeline/retry.go has its own RetryConfig with MaxRetries, BaseDelay, MaxDelay, and jitter. It retries detector errors uniformly. Adding family-based retry semantics would be redundant or conflicting — two systems fighting over the same decision.

C7. Unused features add conceptual weight

go-error-family ships diagnostics (Filesystem, Network, Git, Postgres rules), agent analysis, message templates, and audience/tone metadata. go-finding (a library) would use approximately:

  • Diagnostics: Not applicable (library doesn't run diagnostics on its own errors)
  • Agent: Not applicable (library doesn't do AI analysis)
  • Audience/Tone: Marginal (library doesn't format user messages)
  • Templates: CLI only (useful in cmd/go-finding)

~80% of go-error-family's features would be dead weight in the library layer.

C8. Library consumers don't control error handling

go-error-family is designed for the CLI/HTTP boundary — the place where errors leave the program. But go-finding is a library. Its consumers (other programs) decide how to handle errors at their own boundaries. Adopting CLI-boundary patterns in a library imposes opinions on consumers.

6. Three Adoption Scenarios

Scenario A: Full Replacement — NOT RECOMMENDED

Replace FindingError with errorfamily.Error everywhere

  • Eliminate errors.go, ErrorCategory, all 5 sentinels
  • Replace all 66 fmt.Errorf calls with family constructors
  • Wrap go-error-family.Error in a new struct adding Finding/Position/File
  • Rewrite ~50 test files

Cost: 2-3 days of migration, high regression risk, breaks public API, violates principle #12.

Gain: Unified error type, retry semantics, CLI boundary handling.

Net: Negative — cost far exceeds benefit for a library.

Scenario B: Interface Adoption — RECOMMENDED

Implement go-error-family interfaces on FindingError + CLI boundary

  • Add ErrorCode() string to FindingError → implements Coded
  • Add ErrorFamily() Family with category-to-family mapping → implements Classified
  • Add ErrorContext() map[string]string from File/Position → implements Contextual
  • Keep all existing API, sentinels, categories — zero breaking changes
  • Adopt HandleError in cmd/go-finding/main.go for richer CLI output
  • go-error-family import only in cmd/go-finding/ (not root package)

Cost: ~3-4 hours. Additive only. No existing code changes.

Gain: Interoperability, richer CLI output, retry semantics available when needed.

Net: Strongly Positive

Scenario C: No Adoption

Keep current system unchanged

  • go-finding's error system is already well-designed for its domain
  • 5 categories, 5 sentinels, structured FindingError with domain context
  • The Is()/Unwrap() pattern is idiomatic Go

Cost: None.

Lost opportunity: Machine-readable codes, retry semantics, CLI boundary improvements.

Net: Acceptable but leaves value on the table

7. Recommended Implementation Plan (Scenario B)

Phase 1: Interface implementation on FindingError

// errors.go — add these methods to FindingError:

func (e *FindingError) ErrorCode() string {
    return fmt.Sprintf("finding.%s", e.Category)
}

func (e *FindingError) ErrorFamily() errorfamily.Family {
    switch e.Category {
    case ErrCategoryValidation: return errorfamily.Rejection
    case ErrCategoryIO:         return errorfamily.Transient
    case ErrCategoryParse:      return errorfamily.Corruption
    case ErrCategoryConflict:   return errorfamily.Conflict
    case ErrCategoryInternal:   return errorfamily.Infrastructure
    default:                    return errorfamily.Transient
    }
}

func (e *FindingError) ErrorContext() map[string]string {
    ctx := map[string]string{"category": string(e.Category)}
    if e.File != "" { ctx["file"] = e.File }
    if e.Position != nil { ctx["position"] = e.Position.String() }
    return ctx
}

func (e *FindingError) IsRetryable() bool {
    return e.ErrorFamily().IsRetryable()
}

Note: Import only in the consumer, or define an internal adapter. Root package stays dependency-free by using a sub-package for the bridge.

Phase 2: CLI boundary adoption

// cmd/go-finding/main.go — replace manual error output:

func run() error {
    // ... existing logic ...
}

func main() {
    if err := run(); err != nil {
        os.Exit(errorfamily.HandleError(err))
    }
}

go-error-family is imported only in cmd/go-finding/, which already depends on external packages. Root package remains dependency-free.

Phase 3 (Optional): Per-error codes for specific failure modes

// Instead of generic "finding.io", use specific codes:
finding.NewIOError("backup "+path, err).

9. Open Questions

Q1: Should the category-to-family mapping live in root or a bridge package?

If FindingError implements Classified directly, the root package imports errorfamily. To preserve principle #12, create a finding/errorfamily/ bridge package instead. But this adds indirection. Decision needed.

Q2: Should IO errors be Transient (retryable) or split?

"file not found" is Rejection (permanent). "permission denied" is Rejection (permanent). "disk I/O error" could be Transient. Current ErrCategoryIO bundles them all. Mapping the whole category to Transient would make all IO errors retryable, which is wrong. Per-error code classification may be needed.

Q3: Should pipeline retry logic use Family.IsRetryable()?

Currently retry.go retries everything. Adopting Family-based retry would mean only Transient errors get retried. This changes behavior (less aggressive retry). Could be a feature or a regression depending on detector error patterns.

10. Conclusion

go-error-family is a well-designed library solving a real problem (structured error handling at the CLI/HTTP boundary). But go-finding's error system is also well-designed for its domain (static analysis with Finding/Position context).

The two systems are complementary, not competing. The right move is Scenario B: implement go-error-family's consumer interfaces on FindingError for interoperability, adopt HandleError in the CLI, and keep the domain-specific error type intact.

This gets ~80% of the benefit at ~5% of the cost, with zero breaking changes.
