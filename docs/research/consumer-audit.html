Key Insights

1. The data model IS the product

Finding, Report, Severity, Position, Category, Builder — this is what 15 projects depend on. The library succeeds as a unified type system for static analysis results.

2. SARIF export is the killer feature

8/15 projects use ToSARIF() or WriteSARIF(). It's the standard interchange format. Zero projects import SARIF — it's a write-only interface in practice.

3. Pipeline has near-zero adoption

Only oxlint-auto-configure uses the pipeline for real work. template-AUTHORS wraps it superficially. template-SECURITY imports just the Detector interface. The entire fix engine, conflict detection, retry, metrics, verification system is externally unused.

4. Severity mapping is re-implemented everywhere

5+ projects have hand-rolled mapSeverity(string) Severity functions. ParseSeverity() exists but only 1 project uses it. The API is there but undiscovered.

5. Tool JSON → Finding is a repeated pattern

BuildFlow (5 tool adapters), golangci-lint-auto-configure, oxlint-auto-configure, Code-Quality-Agent (7 adapters), branching-flow (8 converters) — all write similar "tool output → []Finding" converters. A helper would eliminate significant boilerplate.

6. Suppression is dead

The entire suppression system (Suppression, SuppressionKind, NotSuppressed, IsSuppressed()) has zero consumers. It ships but nobody uses it.

Recommendations

1

Promote ParseSeverity() — eliminate duplicated severity mapping

5+ projects re-implement mapSeverity(string) Severity. The function exists but only template-readme uses it. Add godoc examples, reference it from the README, and consider auto-mapping common severity strings ("fatal", "warn", "note") to increase discoverability.

2

Extract pipeline to a separate module

The pipeline package adds complexity and dependency surface that 12/15 consumers don't need. Move to go-finding-pipeline or a sub-module. This keeps the core data model lean and focused. The pipeline can evolve independently without version-locking the core types.

3

Add a ToolConverter helper for tool JSON → Finding

~30 files across 5 projects implement similar "parse tool JSON output → build Finding" patterns. A ToolConverter or Adapter helper with configurable field mapping (JSON path → Finding field) would eliminate hundreds of lines of boilerplate.

4

Deprecate or document dead API as "reserved"

Suppression, Negate(), AnyOf(), ByConfidence(), Severity.Emoji(), CountBySeverity(), FindingsFromSARIF(), etc. Either remove them (pre-v1.0 freedom), mark them as deprecated, or document as "reserved for future use" to set accurate expectations.

5

Promote Combine() / Diff() — hidden aggregation gems

Only BuildFlow uses these, but multiple projects manually merge reports in loops (Code-Quality-Agent, oxlint-auto-configure, template-SECURITY). Better docs and examples would surface these utilities.

6

Invest in a Category mapping registry

3 projects maintain large map[string]Category tables mapping linter names to categories. A shared registry (e.g., CategoryForLinter("gosec") → CategorySecurity) would centralize this knowledge and keep mappings consistent across tools.
