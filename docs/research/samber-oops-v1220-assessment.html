A drop-in structured error library for Go that enriches errors with stack traces, attributes, user/tenant context, and logger integrations. This report evaluates its design, maturity, and fit for the go-finding static-analysis project.

00 — Executive Verdict

Excellent observability library, weak fit for go-finding

Overall assessment: 8.5 / 10 as a library; 3 / 10 as a go-finding dependency

samber/oops is a mature, well-designed observability layer for errors. It captures everything an on-call engineer wants: stack traces, source fragments, structured attributes, trace/span IDs, user/tenant context, and HTTP request/response bodies. It integrates with all major Go loggers and follows semver strictly as a v1 library.

For go-finding, however, the fit is poor. go-finding is a library, not a runtime service. It has no users, tenants, HTTP traffic, distributed traces, or production debugging pipelines. oops would add three runtime dependencies and a large conceptual API surface for problems go-finding does not have.

Recommendation: do not adopt oops in go-finding. If richer error context is ever needed, prefer go-error-family's interfaces (protocol) or lightweight custom types. oops only makes sense if go-finding grows into a long-running service with observability requirements.

Library strengths

  • Mature v1 with strict semver
  • Automatic stack traces + source fragments
  • Rich context: user, tenant, HTTP req/res, trace/span
  • Logger integrations: slog, zap, logrus, zerolog
  • Drop-in error compatibility
  • Go 1.21+ (broader compatibility than go-error-family)

  • Observability belongs to consumers, not the library
01 — Library Overview

What samber/oops is

samber/oops is a structured error library that wraps any Go error in an OopsError carrying rich metadata. It is explicitly not a logging library; it is designed to feed existing logging/observability pipelines.

Core model:

  • Builder API — fluent chain ending in terminal methods like .Errorf(), .Wrap(), .Recover()
  • Context/attributes — .With(key, value) supports any values and lazy func() any evaluation
  • Identity metadata — .Code(), .Trace(), .Span(), .In(), .Tags()
  • Operational metadata — .Hint(), .Owner(), .Time(), .Since(), .Duration()
  • Multi-tenant context — .User(), .Tenant() with flexible attribute formats
  • HTTP capture — .Request(), .Response() with optional body inclusion
  • Stack traces — automatic, pretty-printed, configurable depth and exclusions
  • Panic recovery + assertions — .Recover(), .Assert(), .Assertf()
  • Serialization — MarshalJSON(), ToMap(), LogValuer for slog

v1.22.0 (May 2026) refactored the builder to a functional-options linked list, claiming:

  • -90% error build time, zero allocations when wrapping nil
  • -30% to -90% build time and memory for real errors
  • New: CallerSkip(), FrameSkip(), AsError[T](), Layers(), identity-based Is()

oops asks "what do I know about this error?" and gives a forensic answer. It does not ask "what should the system do with it?"

02 — PRO Arguments

What samber/oops does well

P1. Drop-in replacement for standard errors

OopsError implements the error interface and composes with fmt.Errorf("%w"), errors.Is, and errors.As. Existing code can adopt it incrementally without a full rewrite. 

return oops.Wrapf(dbErr, "could not fetch user %d", id)  // nil if dbErr is nil

P2. Automatic stack traces with rich formatting

Every oops error captures a stack trace. .Stacktrace() pretty-prints it, and .StackFrames() provides raw frames for Sentry-like consumers. Wrapped errors produce annotated multi-layer traces.

P3. Source code fragments

When enabled, .Sources() shows the exact source lines around the error site (Go source files must remain at build-time paths). This is unique among Go error libraries and dramatically speeds up debugging.

P4. Rich, typed context

.With(key, value) accepts any, including lazy func() any. This is far more flexible than string-only context maps and lets callers attach structured data without serializing prematurely.

P5. First-class multi-tenant and HTTP support

.User(), .Tenant(), .Request(), and .Response() are purpose-built for SaaS/microservice debugging. Few Go libraries handle this domain as cleanly.

P6. Logger ecosystem integrations

Native slog.LogValuer plus provided formatters for zap, logrus, and zerolog. Errors serialize as structured log groups without custom marshaling.

P7. Mature project governance

v1 with strict semver, ~959 stars, 41+ releases, automated CI, CodeQL, dependabot, and active maintenance. The v1.22.0 release delivered a major performance rewrite. This is a safe dependency for production services.

P8. Panic recovery and assertions

.Recover() / .Recoverf() convert panics into structured errors. Assertions are documented as an anti-pattern but available for critical invariants. Both integrate cleanly with the builder.

P9. Broad Go version support

Requires Go 1.21+, compared to go-error-family's Go 1.26+ requirement. This makes oops easier to adopt in older codebases.

03 — CONTRA Arguments

Where it falls short or introduces risk

C1. Not actually zero dependencies

The README claims "Zero dependencies, lightweight and fast," but go.mod lists three runtime dependencies: github.com/oklog/ulid/v2 (trace IDs), github.com/samber/lo (utilities), and go.opentelemetry.io/otel/trace (trace/Span correlation). Test dependencies are noted as stripped on release, but the runtime footprint is real.

C2. No behavioral classification

oops answers "what do I know?" but not "what should the system do?" There is no built-in retry/exit-code/audience/tone model. A consumer still has to build that logic around the error metadata.

C3. Heavy API surface for simple use cases

The builder exposes 20+ methods. For a project that just needs stack traces and context, this is overkill. The learning curve and cognitive load are higher than pkg/errors or a small custom type.

C4. Builder copies context maps

The immutable builder copies the context map at each chain step. v1.22.0 improved this, but it is still fundamentally more allocation-heavy than a simple fmt.Errorf("%w") or a static error type.

C5. Source fragments require source at runtime

.Sources() reads Go source files from disk at runtime, so it only works when source files remain at their build locations. This breaks in containers that copy only the binary, and it is disabled by default for that reason.

C6. Hidden wrapping semantics footgun

oops.Wrapf(err, "msg: %w", otherErr) uses %w only for string formatting; it does not chain otherErr. The chain is always result → err. The README explicitly warns about this, but it is a subtle distinction that can surprise users migrating from fmt.Errorf("%w").

C7. OTel integration is incomplete

go.opentelemetry.io/otel/trace is a runtime dependency, but there is no official OTel SDK integration yet. The README solicits contributions for otel and go-sentry. For teams expecting out-of-the-box observability wiring, this is a gap.

C8. Assertions are a documented anti-pattern

The library includes .Assert() / .Assertf() but acknowledges they may be considered an anti-pattern in Go. Their presence adds API surface for a pattern most Go codebases avoid.

04 — Domain Fit for go-finding

How well does it map to static analysis?

go-finding is a library for static-analysis findings. Its errors carry domain context: file path, position (line/column), severity, confidence, category, and a reference to the Finding. oops is designed for runtime services with users, tenants, HTTP traffic, and distributed traces.

go-finding concern oops capability Verdict
Stack traces for debugging Automatic, pretty-printed Useful
File / Position / Finding context Generic With(); no structured static-analysis fields Possible but lossy
Machine-readable error codes .Code(any) — flexible but untyped OK
Retry / exit-code / audience semantics None No fit
User / tenant / HTTP context First-class Irrelevant
Structured logging integration slog, zap, logrus, zerolog Consumer concern
Dependency footprint 3 runtime deps + transitive OTel Heavy for a library

Most of oops's headline features have no natural use in go-finding. Adopting it would be importing a service observability toolkit into a code-analysis library.

05 — Competitive Position

How it compares to alternatives

Library Strength Weakness vs. oops

stdlib fmt.Errorf("%w") Zero deps, idiomatic No structured context or traces

oops and go-error-family are complements, not competitors. oops is for forensic context; go-error-family is for behavioral decisions. The go-error-family project even ships a bridge/ submodule to use both together.

06 — Recommendations

What go-finding should do

Not recommended: adopt oops as a dependency

The dependency cost, API surface, and feature mismatch outweigh any benefit. go-finding does not need user/tenant context, HTTP capture, distributed traces, or panic recovery. Adding oops would violate the project's minimal-dependency philosophy and bloat the binary.

Recommended: do nothing

go-finding's existing error system (FindingError with category, file, position, and cause) is already domain-appropriate. For CLI output, the existing formatting is sufficient. For consumers that want richer handling, the library exposes the data they need.

Alternative: consider go-error-family interfaces instead

If go-finding wants interoperability with a broader error-handling ecosystem, the lightweight path is implementing go-error-family's small interfaces in a bridge subpackage. That adds no runtime dependencies to consumers and preserves the domain model.

When oops would become relevant

If go-finding evolves into a long-running service (e.g., a Language Server, a CI daemon, or a hosted API) with production observability needs, oops would be a strong candidate. Until then, it is premature.
