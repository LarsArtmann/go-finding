Modularization Proposal · 2026-07-01

Unix-Style Module Decomposition

Split the go-finding monolith into four independently versioned Go modules, each with a single clear purpose and zero unnecessary dependencies. Consumers import only what they need — the core Finding type, the pipeline, the analysis bridge, or the CLI.

Scope: full modularization Base: v1.0.0 Status: ready for execution

00Executive Summary

go-finding is a single-module Go library (github.com/larsartmann/go-finding) with 12 packages and 37 production files in the root alone. Every consumer who imports the core Finding type transitively pulls in golang.org/x/tools, golang.org/x/sync, gogenfilter, go-faster/yaml, and go-output — even if they only need the type definitions.

The root package itself is zero-dependency (stdlib only). All external dependencies live in sub-packages. This is the ideal starting point for Unix-style decomposition: each concern becomes its own module, and consumers compose only what they need.

The bottom line Split into 4 modules: core (zero deps), pipeline (x/sync + gogenfilter), analysis (x/tools), and CLI (yaml + go-output). No import path changes. No breaking changes for consumers. Dual go.work + replace strategy for development and CI isolation.

02Proposed Module Structure

Four modules, each doing one thing well, composable like Unix pipes.

03DAG Verification

The proposed dependency graph is a strict DAG — no cycles possible:

Layer 0 Layer 1 Layer 2 ┌─────────┐ ┌──────────┐ ┌─────────────┐ │ core │ ←── │ pipeline │ ←── │ CLI │ │(stdlib) │ ←── │ analysis │ │ (yaml, ...) │ └─────────┘ └──────────┘ └─────────────┘ ↑ ↑ │ pipeline/goast (in pipeline module) │ gotoken (in core module)
Acyclic proof core → nothing. pipeline → core. analysis → core. CLI → core + pipeline. No module depends upward. No module depends on a leaf. The graph is trivially acyclic.

04Dependency Isolation

The primary benefit: each module carries only the dependencies it actually needs.

Dependency Monolith (current) After split
golang.org/x/tools In shared go.mod analysis module only
golang.org/x/sync In shared go.mod pipeline module only
gogenfilter In shared go.mod pipeline + CLI only
go-faster/yaml In shared go.mod CLI module only
go-output In shared go.mod CLI module only
Core consumer gets ALL of the above ZERO external deps

Test Dependencies

ginkgo/v2 and gomega are used in BDD tests across root and pipeline. Go has no test-only require block, so these appear in each module's go.mod that has BDD tests. This is acceptable — most modules should have zero test framework deps in production builds.

05Replace & Workspace Strategy

Dual strategy — both go.work and replace directives.

Replace directives (GOWORK=off CI/consumer builds)

Each sub-module that depends on a sibling gets a replace directive:

# pipeline/go.mod
require github.com/larsartmann/go-finding v0.0.0
replace github.com/larsartmann/go-finding => ../

# analysis/go.mod
require github.com/larsartmann/go-finding v0.0.0
replace github.com/larsartmann/go-finding => ../

# cmd/go-finding/go.mod
require github.com/larsartmann/go-finding v0.0.0
require github.com/larsartmann/go-finding/pipeline v0.0.0
replace github.com/larsartmann/go-finding => ../
replace github.com/larsartmann/go-finding/pipeline => ../pipeline
v0.0.0 normalization All internal requires use v0.0.0 — replace makes the version irrelevant for resolution, eliminating pseudo-version churn.

06Error Type Placement

All error types (FindingError, ErrValidation, ErrIO, etc.) live in the core module. This is correct: they are part of the Finding domain contract, and every consumer already imports core. No cross-module errors.Is/errors.As issues.

Pipeline-specific errors (e.g., errAlreadyRan) stay in the pipeline module. They are implementation details, not contract errors.

07Versioning Strategy

Shared versioning — single v* git tag bumps all modules together. Appropriate because:

  • Single team, single repo
  • Modules are tightly coupled (pipeline always tracks core changes)
  • Currently at v1.0.0 — no major version suffix needed in paths

11Build System Impact

flake.nix

The current flake.nix builds with buildGoModule using a single src and vendorHash. With GOWORK=off set in devShells, the replace directives resolve sibling modules from the source tree. The vendorHash will change after modularization — update after go mod tidy.

CI (GitHub Actions)

Current CI runs go build ./... and go test ./... from root. With go.work, these commands still work from root (workspace mode). For per-module isolation, add a CI job running GOWORK=off go build ./... in each module directory.

goreleaser

goreleaser builds ./cmd/go-finding. After modularization, this still works with go.work. For GOWORK=off release builds, replace directives resolve the sibling modules. No goreleaser config changes needed.
