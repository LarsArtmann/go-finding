Bottom line: architecture is sound, two surgical improvements unlock the next stage

Layering is correct (CLI → pipeline → root, no cycles). Root package stays dependency-free as designed. Plugin architecture (DetectorRegistry, FixProvider, FindingProcessor) makes the system composable without code changes. Two issues prevent an A grade: pipeline/ is a 22-file mega-package that should split by concern, and pipeline/adapters.go re-exports root types for backward compat — a leaky boundary. Neither is urgent; both are batchable into v1.0.

01Findings

pipeline/ is a 22-file mega-package

pipeline/ holds 22 production .go files (~11K LOC) covering six distinct concerns: orchestration (pipeline.go, pipeline_detect.go, pipeline_iteration.go), config (config.go, config_file.go), fix engine (fix_engine.go, fix_provider.go, fix_applier.go, fix_edit.go, fix_provider_helpers.go), conflict (conflict.go), infrastructure (file_backup.go, line_shift.go, retry.go, partial.go, metrics.go), and stages/hooks (stage.go, stage_hook.go, verify.go, adapters.go, generated_filter.go, result.go). Each file is well-named; the problem is they all share one package namespace. A reader looking for "how fixes are applied" must search 5 files in one flat directory.

pipeline/adapters.go leaks root types across the boundary

Lines 12-24 of pipeline/adapters.go re-export Detection, DetectorFunc, and NamedDetectorFunc from the root package via type aliases and a var alias. Comment says "for backward compatibility." This means import paths are ambiguous (finding.Detector vs pipeline.Detector) and the pipeline package re-exposes the root package's surface area.

Composition via interfaces is exemplary

Four interfaces define every extension point: Detector (produces findings), FixProvider (produces edits), FindingProcessor (transforms findings), StageHook (observes pipeline events). Combined with DetectorRegistry (thread-safe plugin registry) and ToolAdapter[O] (generic output converter), the library achieves composability without DI frameworks. Service-orientation at the package level.

02Issue Cards

Important · Modularity blocker

pipeline/ mega-package

pipeline/*.go · 22 files · ~11K LOC

Single package covering six concerns. Forces flat file browsing; couples unrelated changes (a conflict-detection edit touches the same package as a metrics change).

Fix (v1.0, mechanical, non-breaking for imports of pipeline root types) Split into subpackages keeping pipeline as the facade:
  • pipeline/fix — fix_engine, fix_provider, fix_applier, fix_edit, fix_provider_helpers, line_shift
  • pipeline/conflict — conflict
  • pipeline/config — config, config_file
  • pipeline/infra — file_backup, retry, partial, metrics
  • pipeline (root) — pipeline.go, pipeline_detect.go, pipeline_iteration.go, stage.go, stage_hook.go, verify.go, adapters.go, generated_filter.go, result.go
Use re-export type aliases in pipeline for backward compatibility. Net: package count goes from 5 to 9, each under 1K LOC.
Nice to have · Boundary hygiene

adapters.go backward-compat re-exports

pipeline/adapters.go:12-24

Three re-exports of root types: type Detector = finding.Detector, type DetectorFunc = finding.DetectorFunc, var NamedDetectorFunc = finding.NamedDetectorFunc. The comment marks them deprecated but they remain.

Fix (v1.0) Remove the re-exports when the v1.0 API lock happens. Update internal callers (3 sites). Document in MIGRATION_v1.0.md. Cuts the pipeline→root leak entirely.
Strength · Service-orientation

Plugin architecture achieves SOA at library level

registry.go · detector.go · pipeline/adapters.go · pipeline/fix_provider.go

Each detector is a service implementing Name() + Detect(ctx). Each fix provider is a service implementing Name() + CanHandle() + Edits(). Services register themselves into DetectorRegistry at runtime. The pipeline is the orchestrator that consumes them. This is textbook service-orientation without the network.

Architectural Strengths

+
Zero import cycles Verified by tracing every larsartmann/go-finding import. Direction is strictly CLI → pipeline → root.
+
Root package is the dependency sink Domain types (Finding, Severity, Position, etc.) import only stdlib. Anyone can consume the model without paying for the pipeline.
+
Optional deps isolated go/parser lives in pipeline/goast only. golang.org/x/tools lives in analysis/ only. gogenfilter lives in pipeline/generated_filter.go only. Each is opt-in.
+
Composable via small interfaces Four interfaces, all single-purpose. DetectorRegistry + ToolAdapter[O] turn the library into a plugin host.
+
Pipeline orchestration is decoupled from stages pipeline.go + pipeline_detect.go + pipeline_iteration.go form a tiny orchestrator. Each stage (detect, triage, apply, verify) is independently testable. stage_hook.go lets external code observe every stage transition.
+
CLI is a thin composition root cmd/go-finding only wires together the pipeline, detectors, providers, and output formats. No business logic. Exactly what a CLI should be.

03Action Plan

1

v1.0: Remove pipeline/adapters.go backward-compat re-exports

Delete type Detector = finding.Detector + 2 siblings. Update 3 internal call sites. Document in MIGRATION_v1.0.md.

2

v1.0: Split pipeline/ into subpackages

Five subpackages (fix, conflict, config, infra, plus the existing goast). pipeline root stays as orchestrator + re-export facade. Mechanical change; tests stay in their subpackages.

3

v1.0: Rename FindingProcessor → FindingTransformer

Per naming-review. Aligns interface name with its actual purpose (transform, not "process"). Pairs naturally with the package split — FindingTransformer lives in pipeline root.
